# Topic 1:  What is Load Balancing? (Deep Dive beyond Chapter 1 basics)

## Intuition First (The Why)
Imagine a massive highway funneling into a multi-lane toll plaza. Without organization, every car piles into lane one while lanes three and five sit empty, and if a toll booth catches fire, cars keep driving into the flames. The load balancer is the intelligent traffic system above the plaza: it watches every lane, directs each car to the best one, closes broken lanes instantly, and reopens them when they are repaired.

At a deeper level, a load balancer is a **decoupling mechanism**. Clients only ever know one stable address (a Virtual IP or domain name). Behind that address, servers can be added, removed, restarted, or replaced at any time without the client noticing. This decoupling is what makes horizontal scaling and zero-downtime operations possible.

---

## Detailed Explanation

A **Load Balancer (LB)** is a component (hardware or software) that distributes incoming network traffic across a group of backend servers, called a server pool or farm.

### Core Responsibilities
1. **Even Distribution:** Spread requests so no server is overloaded while others idle.
2. **High Availability via Health Checks:** Continuously probe backends. Remove dead servers from rotation within seconds; add them back when healthy.
3. **Single Entry Point:** Hide internal topology behind one address (the Virtual IP).
4. **Offloading:** Terminate SSL/TLS, compress responses, and absorb slow-client connections so backends stay free for real work.

### The Evolution of Load Balancers
1. **Hardware Appliances:** Physical boxes (F5 BIG-IP, Citrix ADC). Extremely fast but expensive, rigid, and hard to automate.
2. **Software Reverse Proxies:** Nginx, HAProxy, Envoy running on commodity servers. Scalable, scriptable, and the industry default.
3. **Cloud-Native and Service Mesh:** Managed cloud balancers (AWS ALB/NLB, GCP Load Balancing) and decentralized sidecar proxies (Envoy in Istio/Linkerd) where every service instance carries its own micro load balancer.

---

## Mental Model and Analogy
- **The Greeter:** The restaurant greeter who watches all cashier lines and sends each customer to the shortest one. If a register breaks, the greeter stops sending customers there.
- **Switchboard vs Concierge:** A Layer 4 load balancer is an old telephone switchboard operator: blind to conversation content, purely plugging cables by extension number, extremely fast. A Layer 7 load balancer is a hotel concierge: it listens to what you actually need and routes you to the right department, and can refuse you if you lack permission.

---

## Where Load Balancers Live: The Multi-Tier Funnel
Production systems never use a single load balancer. They use a funnel of them:

1. **Tier 1 - DNS / Global Server Load Balancing:** Routes users to the nearest geographic region. Slow to change, but the first line of defense.
2. **Tier 2 - Edge Load Balancer (Layer 7):** The public gateway. Handles SSL termination, security (WAF, DDoS absorption), and URL-based routing (/api vs /static).
3. **Tier 3 - Internal Load Balancer (Layer 4 or 7):** Lives inside the private network, routing traffic between microservices (Checkout Service to Inventory Service).

---

## Layer 4 vs Layer 7

| Feature | Layer 4 (Transport) | Layer 7 (Application) |
| :--- | :--- | :--- |
| Routes based on | IP address and port only | HTTP content: URL, headers, cookies |
| Speed | Extremely fast (kernel-level) | Slower (must decrypt and inspect payload) |
| Intelligence | Blind to application data | Smart routing, auth checks, path-based rules |
| Typical use | Raw TCP/UDP, massive throughput | Web APIs, microservices, WAF |

---

## Algorithms at a Glance
(Deep dive in Topic 2; memorize the list now)
- **Round Robin:** Fixed rotating order.
- **Weighted Round Robin:** Proportional to server capacity.
- **Least Connections:** Send to the server with fewest active connections.
- **Least Response Time:** Send to the fastest-responding server.
- **IP Hash:** Same client IP always reaches the same server.
- **Random:** Uniform random selection; acceptable at large scale.

## Internal Working: The Hidden Machinery

**1. Health Checks**
The LB sends periodic probes (HTTP ping or TCP connect) to each backend. After N consecutive failures, the backend is marked unhealthy and removed from rotation. Active probes run continuously; passive monitoring also watches real traffic for errors and timeouts.

**2. Connection Multiplexing (Connection Pooling)**
Browsers open many short-lived connections. TCP and TLS handshakes are CPU-expensive. A Layer 7 LB maintains a small pool of long-lived Keep-Alive connections to the backends, and multiplexes thousands of short client connections over them. Result: 10,000 concurrent users may be served over only 50 backend connections, freeing backend CPU for application logic.

**3. Connection Draining (Graceful Shutdown)**
During deployments, a backend enters "draining" state: the LB stops sending NEW requests but lets in-flight requests finish (until a timeout, e.g., 30 seconds). Only then is the server restarted. This is the mechanism behind zero-downtime deployments.

**4. Sticky Sessions**
For legacy stateful apps, the LB can pin a user to one server via IP hash or cookie. It works, but it imbalances load and breaks failover. The modern fix is stateless servers plus a shared session store (Redis).

---

## Real-World Examples
1. **AWS:** The Network Load Balancer (NLB) is Layer 4 for ultra-high-throughput TCP/UDP; the Application Load Balancer (ALB) is Layer 7 for intelligent HTTP routing. The split maps exactly to the speed-vs-intelligence trade-off.
2. **Netflix:** Edge balancers (historically Zuul, now Envoy-based) terminate streaming requests; internal service-to-service traffic uses client-side balancing where the caller picks the best instance itself.
3. **Startups:** A single Nginx or HAProxy instance in front of a small server pool is the universal first architecture, later replaced by cloud LBs and Kubernetes Ingress.

---

## Advantages, Disadvantages, and Trade-offs
- **Advantages:** Enables horizontal scaling; provides automatic failover; hides backend churn; centralizes security and encryption; enables zero-downtime deploys via draining.
- **Disadvantages:** Adds one network hop; becomes a Single Point of Failure unless made redundant; adds configuration and operational complexity.
- **Core Trade-off:** Intelligence (Layer 7) vs raw speed (Layer 4). Decrypting and inspecting traffic burns CPU; blind packet flipping is fast but cannot route by content. Choose per tier, not per ideology.

---

## Common Misconceptions
1. "DNS Round-Robin is a good load balancer." False. DNS responses are cached by ISPs per TTL, so dead servers keep receiving traffic for minutes or hours, and DNS performs no active health checks.
2. "A load balancer makes slow servers faster." False. It only distributes work. A missing index or bad query stays slow on every server.
3. "Load balancers are only for web traffic." False. They route database read traffic, gRPC microservice calls, and queue consumers too.
4. "You should put a generic LB directly in front of a database." Usually false. Databases need stateful connection poolers (PgBouncer, ProxySQL), not generic network balancers.
5. "The load balancer can never be the bottleneck." False. All traffic crosses it, which is why production uses redundant pairs (active-passive with floating IP) or multiple LBs behind DNS.

---

## Interview Questions
1. "What is a load balancer and what problems does it solve?" (Distribution, failover via health checks, single entry point, enabling horizontal scaling.)
2. "Why is DNS Round-Robin insufficient for high availability?" (Caching and TTLs keep sending traffic to dead servers; no active health checks.)
3. "Explain Layer 4 vs Layer 7 and when you would use each." (L4 for raw TCP/UDP throughput; L7 for HTTP-aware routing, security, and offloading.)
4. "What is connection multiplexing and why does it help backends?" (Thousands of short client connections served over a few persistent backend connections, saving handshake CPU.)
5. "How do you deploy new code with zero downtime?" (Connection draining: stop new traffic, finish in-flight requests, then restart.)
6. "How do you prevent the LB itself from becoming a single point of failure?" (Active-passive pair with floating IP, or multiple LBs behind DNS round robin.)

---

## Industry Implementation
Kubernetes bakes load balancing into the platform: kube-proxy distributes traffic across pods at Layer 4, and an Ingress controller (Nginx or Envoy) provides Layer 7 routing. In service meshes (Istio, Linkerd), an Envoy sidecar next to every pod performs per-request balancing, retries, and circuit breaking, eliminating the centralized bottleneck entirely. Deployments in these environments rely on readiness probes plus connection draining to achieve zero-downtime releases.

---

## AI/ML System Design Perspective
Load balancing GPU inference is harder than balancing web servers because request costs are wildly non-uniform: one prompt takes 100ms, another 30 seconds. Round robin would pile long jobs onto busy GPUs while others idle. Modern LLM serving stacks use **load-aware routing**: the router queries each worker's queue depth and KV-cache memory usage and assigns the request to the least burdened GPU. Routers may also split traffic by payload size, sending small prompts to cheap fast model pools and heavy reasoning jobs to expensive large-model pools.

---

## Revision Sheet
- **Definition:** Decoupling layer that distributes traffic, hides backend topology, and provides availability.
- **Jobs:** Distribution, health-check failover, single entry point (VIP), SSL/offloading.
- **Evolution:** Hardware appliances, software proxies (Nginx/HAProxy), cloud LBs, service mesh sidecars.
- **Funnel:** DNS/GSLB, then Edge L7, then Internal L4/L7.
- **L4 vs L7:** Fast and blind vs slower and content-aware.
- **Hidden machinery:** Health checks, connection multiplexing, connection draining, sticky sessions.
- **DNS is not an LB:** No health checks, poisoned by caching.
- **Redundancy:** LBs must themselves be redundant to avoid a SPOF.

# Topic 2: Load Balancing Algorithms: Static vs Dynamic

## Intuition First (The Why)
Imagine you manage checkout lanes at a supermarket, and a stream of customers arrives with carts of wildly different sizes.

A **static** strategy is a fixed rule written on a poster: "Every 3rd customer goes to lane 3." It costs nothing to run and never needs observation, but it is blind: if lane 3's cashier calls in sick or a customer arrives with a full furniture cart, the rule does not care.

A **dynamic** strategy is a live dispatcher standing at the entrance, watching lane lengths and cashier speeds, and assigning each customer to the best lane right now. It adapts beautifully, but it requires constant observation (state), and it can overreact: if one cashier sneezes and slows for ten seconds, the dispatcher starves that lane, then over-floods it when they recover.

Every load balancing algorithm is one of these two philosophies. Static algorithms trust your configuration. Dynamic algorithms trust your telemetry. Both can lie, and knowing when each lies is the entire topic.

---

## Detailed Explanation

### Family 1: Static Algorithms
Static algorithms make routing decisions from fixed configuration alone. They keep little or no live state about server load.

**1. Round Robin (RR)**
- How: Maintain a counter; send request i to server (i mod N).
- State: A single counter.
- Use when: Requests are uniform in cost and servers are identical (simple static asset serving, homogeneous API calls).
- Fails when: Request costs vary (one request takes 5ms, another 5s), server capacities differ, or connections are long-lived (WebSockets): assignment happens once at connect time, so a server that received ten 2-hour connections looks "idle" to the counter.

**2. Weighted Round Robin (WRR)**
- How: Like RR, but each server gets a number of turns proportional to its weight (capacity). A server with weight 5 gets five times the traffic of a server with weight 1.
- The burst problem: A naive implementation sends all of a server's turns consecutively (weights 5,1,1 gives A A A A A B C), creating micro-bursts that spike latency.
- The fix, Smooth WRR (used by nginx): Interleave the turns using a current-weight accumulator so the sequence spreads evenly. For weights A=5, B=1, C=1, smooth WRR produces A A B A C A A instead of AAAAA B C. This is a genuinely interview-worthy detail.
- Fails when: Actual capacity drifts from configured weights (noisy neighbors, thermal throttling, cold caches). Weights are a static guess.

**3. IP Hash / Source Address Hash**
- How: hash(client IP) mod N selects the server. The same client always reaches the same server.
- Use when: You need cheap session locality or cache affinity without cookies.
- Fails when, part one: Client IPs cluster. Mobile carriers use CGNAT, putting thousands or millions of users behind a single public IP. All of them hash to one server, creating a brutal hotspot while siblings idle. This has taken down real production systems.
- Fails when, part two: Adding or removing a server changes N, so (hash mod N) remaps nearly every client to a different server, destroying all locality and cache warmth. (Consistent Hashing, our Topic 10, exists precisely to fix this.)

**4. Random and Weighted Random**
- How: Pick a server uniformly at random, or with probability proportional to weight.
- Insight: By the law of large numbers, random converges to even distribution at high request counts, with zero coordination state. It is used in several client-side balancers.
- Fails when: Traffic volume is low (variance dominates), or costs vary (same blindness as RR).

### Family 2: Dynamic Algorithms
Dynamic algorithms route using live telemetry: connection counts, response times, or resource usage.

**1. Least Connections (LC)**
- How: Track active connection count per backend; send the new request to the smallest.
- State: One integer per backend, incremented on connect, decremented on disconnect.
- Use when: Request durations vary widely (long polls, WebSockets, mixed short/long API calls). This is the default recommendation for session-heavy workloads (HAProxy docs famously recommend leastconn for long sessions).
- Fails when: Connection count diverges from actual work. With HTTP Keep-Alive, a backend can hold hundreds of idle persistent connections doing nothing, while another backend with five connections is burning CPU on heavy jobs. Count measures occupancy, not effort.

**2. Weighted Least Connections (WLC)**
- How: Compare (active connections / weight) and pick the minimum. Gives stronger servers proportionally more connections.
- Use when: Variable durations AND heterogeneous hardware. This is the workhorse of real mixed fleets.

**3. Least Response Time (LRT)**
- How: Route to the backend with the best recent response time, often combined with connection count (for example, nginx least_time, HAProxy with observability agents).
- The measurement problem: Raw averages are poisoned forever by an old outage; the last single sample is too noisy. Production systems use an **EWMA (Exponentially Weighted Moving Average)**: new_average = alpha times sample plus (1 minus alpha) times old_average. Recent samples dominate, old ones decay exponentially. Choosing alpha is a tuning decision: high alpha reacts fast but jitters; low alpha is smooth but slow to notice a degraded server.
- Fails when: Feedback loops cause herding and oscillation. A server slows slightly, the LB drains it, its queue empties, it becomes "fastest", the LB floods it, it slows again. EWMA damping and request-cost awareness mitigate but never fully eliminate this.

**4. Resource-Based / Agent-Based**
- How: An agent on each server reports real CPU, memory, or queue depth (historically via SNMP); the LB routes on true saturation.
- Use when: Work per request correlates strongly with a measurable resource.
- Fails when: Operational complexity. You now deploy, secure, and monitor an agent fleet. Largely superseded by in-protocol signals (queue depth over gRPC, or load reports in service meshes).

**5. Power of Two Choices (P2C) - The Modern Gem**
- How: Pick two backends uniformly at random; route to the better of the two by your chosen metric (connections, EWMA latency, queue depth).
- Why it is brilliant: Querying all N backends costs O(N) state and coordination. Mitzenmacher's classic result shows that just two random probes reduce the maximum load imbalance exponentially compared to one random choice. You get near-optimal balance with O(1) work and no shared state.
- Bonus: It degrades gracefully when multiple LB instances each hold only a partial view of global load, which is exactly the multi-LB production reality.
- Where it lives: Envoy's least_request policy uses P2C by default; gRPC and many client-side balancers use it.

**6. Queue-Depth / Load-Aware Routing (The AI Era)**
- How: The router asks each worker for its current pending queue depth or GPU memory pressure and routes to the least burdened.
- This is the dynamic family taken to its logical end: the metric is no longer a proxy (connections, latency) but the actual scarce resource. Covered further in the AI/ML section.

---

## Mental Model and Analogy
- **Static (RR/WRR):** A printed shift rota. Fair on paper, blind in reality.
- **Dynamic (LC/LRT):** A floor manager with a live dashboard. Adaptive, but can panic.
- **P2C:** Instead of surveying all forty checkout lanes (expensive), you glance at two random lanes and join the shorter. Near-optimal, almost free.
- **EWMA:** Judging a cashier by their last twenty customers with recent ones counting double, rather than by their entire career or by the single customer currently yelling.

## Real-World Examples

1. **The CGNAT Disaster (ip_hash failure):** A European service used source-IP hashing for cache locality. After a mobile carrier rolled out CGNAT, roughly two million mobile users appeared from one public IP. One backend absorbed all of them and melted while seven siblings idled at 4% CPU. The fix was abandoning ip_hash for cookie-based persistence plus P2C.
2. **HAProxy for Long Sessions:** Platforms with long-lived sessions (VPNs, trading dashboards) default to leastconn, because round robin would pile new hour-long sessions onto servers already holding hundreds.
3. **Envoy in Service Meshes:** Istio and Linkerd ship least_request with Power-of-Two-Choices as a recommended policy, precisely because each sidecar proxy only sees its own partial traffic view, and P2C tolerates partial information gracefully.
4. **nginx Smooth WRR:** nginx's default weighted round robin implements the smooth interleaving algorithm described above, which is why weighted fleets behind nginx do not show sawtooth latency spikes.

---

## Internal Working: State, Partial Views, and Warm-Up

1. **What state each algorithm keeps:** RR keeps a counter; WRR keeps weights plus an accumulator; LC keeps an integer per backend; LRT keeps an EWMA per backend; P2C keeps whatever metric you compare but only reads two entries per decision.
2. **The multi-LB partial-view problem:** With M load balancer instances, each tracks only the traffic it personally forwarded. Global least-connections becomes M separate guesses, and imbalance persists. P2C and latency-based metrics degrade gracefully here; strict global LC does not. This is a senior-level interview point.
3. **Slow start / warm-up:** A freshly restarted server has cold caches, cold JIT, and empty connection pools. Giving it full weight instantly causes a latency spike and can trigger false health-check failures. Production LBs ramp weight gradually: HAProxy slowstart, Envoy slow_start_mode, nginx Plus slow_start. Dynamic algorithms must respect warm-up or they will punish exactly the servers that just recovered.
4. **Interaction with health checks:** Unhealthy backends are removed from the candidate set before any algorithm runs. Some systems also apply dynamic weights from agent checks, blending static and dynamic families.

---

## Advantages, Disadvantages, and Trade-offs

- **Static advantages:** Zero telemetry overhead, deterministic, trivially debuggable, no feedback loops.
- **Static disadvantages:** Blind to real load; wrong the moment reality diverges from configuration.
- **Dynamic advantages:** Adapts to variable costs, heterogeneous hardware, and degradation; self-healing distribution.
- **Dynamic disadvantages:** State and CPU overhead; feedback oscillation; partial-view errors across multiple LBs; harder to debug ("why did traffic move?" has no simple answer).
- **The core trade-off:** Configuration trust vs telemetry trust. Uniform, homogeneous, short-lived workloads favor static. Variable, heterogeneous, long-lived, or expensive workloads favor dynamic.

---

## Common Misconceptions

1. "Least connections always balances load." False. With Keep-Alive idle connections or compute-heavy single connections, count diverges from effort.
2. "Round robin is fair." Only when every request costs the same. One 30-second report request ruins fairness for an hour.
3. "ip_hash distributes evenly." False. CGNAT, corporate proxies, and CDN edge IPs cluster millions of users behind single addresses.
4. "Dynamic algorithms are strictly better." False. They add oscillation risk, state overhead, and partial-view errors. For a uniform three-server static fleet, RR is cheaper and equally good.
5. "Weights solve heterogeneous fleets permanently." False. Weights are a snapshot guess; noisy neighbors and cold caches make real capacity drift daily.

## Industry Implementation

- **nginx:** round robin (smooth weighted), least_conn, ip_hash, random, hash directives.
- **HAProxy:** roundrobin (smooth), leastconn, source, first, static-rr, plus slowstart and agent-based dynamic weights.
- **Envoy / service mesh:** ROUND_ROBIN, LEAST_REQUEST (P2C), RING_HASH, MAGLEV, RANDOM, with locality-weighted and slow-start options.
- **Cloud:** AWS ALB targets use round robin; NLB uses flow-hash; Kubernetes IPVS mode exposes rr, lc, dh, sh and more.
- **Client-side:** gRPC and Cassandra drivers implement P2C and latency-aware policies inside the client, removing the central hop entirely.

---

## AI/ML System Design Perspective

LLM serving pushed dynamic balancing to its extreme, because request cost varies by orders of magnitude and the scarce resource is GPU memory, not CPU:
- **Queue-depth routing:** Routers (for example in vLLM or SGLang deployments) assign requests to the worker with the shortest pending queue and most free KV-cache memory, not the fewest connections.
- **Prefix-cache-aware routing (cutting edge):** If worker B already holds the KV cache for a system prompt or a long document prefix, routing a related request to B skips recomputation entirely. Modern routers therefore balance not just load but cache affinity, a hybrid of dynamic load metrics and ip-hash-style locality, done correctly with consistent hashing instead of mod-N.
- This is the full circle of the topic: static locality (ip_hash) failed due to hotspots; dynamic load routing failed to see cache value; the state of the art fuses both.

---

## Revision Sheet

- **Static family:** RR, Weighted RR (smooth), IP hash, Random. Zero telemetry, blind to reality.
- **Dynamic family:** Least Connections, Weighted LC, Least Response Time (EWMA), agent-based, P2C, queue-depth.
- **RR fails:** variable cost, long-lived connections, heterogeneous hardware.
- **WRR detail:** naive bursts; smooth WRR interleaves (A A B A C A A for 5,1,1).
- **IP hash fails:** CGNAT hotspots; mod-N remapping on fleet changes.
- **LC fails:** idle Keep-Alive connections inflate counts; count is occupancy, not effort.
- **LRT needs EWMA:** decay old samples; avoid herding oscillation.
- **P2C:** two random probes, exponential imbalance reduction, O(1) state, tolerant of partial views.
- **Production must-haves:** slow start / warm-up, health-check integration, multi-LB partial-view awareness.

# Topic 3: Layer 4 vs Layer 7 Load Balancing

## Intuition First (The Why)
Imagine the postal service delivering millions of letters a day to a massive corporate headquarters.

**Layer 4 (The Sorting Facility):** The postal workers only look at the outside of the envelope. They read the Zip Code (IP Address) and the PO Box number (Port Number). They throw the mail into the correct bin and move on. They process 10,000 envelopes a minute. They have no idea if the letter inside contains a lawsuit, a birthday card, or a bomb. 

**Layer 7 (The Executive Assistants):** The mail is brought to a desk of assistants who physically open every envelope, read the contents, and make decisions. "This is a legal contract, send it to the General Counsel. This is a check for $10,000, send it to Accounting. This is spam, throw it in the trash." They process 50 letters a minute. They are incredibly smart, but they require massive effort and time.

In system design, you must decide if your traffic needs to be sorted by address (Layer 4) or read and understood (Layer 7). Choosing wrong will either bankrupt you in CPU costs or cripple your application's routing logic.

## Detailed Explanation: The OSI Model Reality

To understand load balancing, you must understand what the load balancer is actually looking at in the network packet.

### Layer 4: The Transport Layer (TCP/UDP)
A Layer 4 load balancer operates at the transport layer of the OSI model. 
- **What it sees:** Source IP, Source Port, Destination IP, Destination Port, and Protocol (TCP or UDP).
- **What it cannot see:** The payload. It cannot see HTTP headers, URL paths, cookies, or JSON bodies. The payload is just an encrypted or opaque stream of bytes to the LB.
- **How it routes:** It forwards the raw TCP/UDP packets to a backend server based purely on the IP and Port combination.

### Layer 7: The Application Layer (HTTP, gRPC, WebSockets)
A Layer 7 load balancer operates at the application layer.
- **What it sees:** Everything Layer 4 sees, PLUS the actual application payload. It parses HTTP methods (GET, POST), URLs (`/api/v1/checkout`), HTTP headers (`Host: api.example.com`, `User-Agent`), cookies, and sometimes even the JSON body.
- **What it does:** It acts as a full network proxy. It terminates the client's TCP connection, reads the HTTP request, opens a completely new TCP connection to the backend server, and forwards the HTTP request. 
- **How it routes:** It makes decisions based on the content of the message.

- **Layer 4 is the Club Bouncer:** Checks your ID (IP/Port). If you are on the VIP list (allowed IP range), you get in. The bouncer doesn't care what you do inside or who you talk to. 
- **Layer 7 is the Hotel Concierge:** Listens to your request ("I need a vegan dinner reservation and a taxi to the airport"). Based on the exact words you say, the concierge routes you to the restaurant or the valet stand.

## Internal Working: The Hidden Mechanics

### 1. Layer 4 Connection Tracking (Conntrack)
Many assume Layer 4 is "stateless" because it doesn't read HTTP. This is false. For TCP traffic, an L4 LB must maintain a **Connection Tracking Table (Conntrack)** in RAM. 
- When Client A connects to the VIP, the LB records `{Client A IP:Port -> Backend Server 2}`.
- When the response comes back from Backend Server 2, the LB checks the table to know it must send the packet back to Client A.
- **The Bottleneck:** If you have 10 million concurrent connections, the L4 LB must store 10 million state entries in RAM. This is often the scaling limit of L4 load balancers, not CPU.

### 2. Layer 4 Direct Server Return (DSR)
To bypass the RAM/CPU bottleneck of Conntrack and the bandwidth bottleneck of routing return traffic through the LB, high-performance L4 LBs use **DSR (or L4DR)**.
- The LB only intercepts *incoming* requests. It rewrites the destination MAC address (not the IP) to the backend server's MAC and forwards it.
- The backend server receives the packet, sees the destination IP is the VIP (which is configured on a loopback interface on the server), and processes it.
- **The Magic:** The backend server sends the response *directly* to the client's IP, completely bypassing the load balancer on the return trip. The LB only handles ingress. This allows L4 LBs to handle massive DDoS attacks or video streaming egress without bottlenecking.

### 3. Layer 7 TLS Termination vs. Pass-Through
- **TLS Termination (Offloading):** The client connects to the L7 LB via HTTPS. The LB holds the SSL certificate, decrypts the traffic into plain HTTP, reads the URL, and sends plain HTTP to the backend. 
  - *Pro:* Backend servers don't waste CPU on cryptography; L7 LB can read the payload.
  - *Con:* Traffic between the LB and the backend is unencrypted (only safe on a private internal network).
- **TLS Pass-Through:** The L4 LB (or an L7 LB acting as L4) just forwards the encrypted TCP stream. The backend server must hold the certificate and decrypt it.
  - *Pro:* End-to-end encryption.
  - *Con:* The LB cannot read the URL or headers to make routing decisions; backend CPUs are burned on cryptography.

### 4. The HTTP/2 and gRPC Trap
HTTP/1.1 opens a new TCP connection for almost every request. L7 LBs easily balance this by distributing connections. 
**HTTP/2 and gRPC** multiplex hundreds of requests over a *single, long-lived TCP connection*. 
If you put a standard L4 LB or a naive L7 LB in front of gRPC, it will route the single TCP connection to Server A. Server A will receive 10,000 gRPC requests, while Server B receives zero. 
**The Fix:** The L7 LB must be "stream-aware." It must terminate the TCP connection, parse the HTTP/2 frames, and load balance *per-stream* (per-request), not per-connection. Envoy is famous for handling this correctly.

## Real-World Examples

1. **AWS NLB (Network Load Balancer):** This is AWS's ultra-high-performance Layer 4 LB. It operates at the connection level, supports DSR-like architectures, and can handle millions of requests per second with ultra-low latency. Used for gaming servers (UDP) and massive TCP ingestion pipelines.
2. **AWS ALB (Application Load Balancer):** AWS's Layer 7 LB. It reads HTTP headers, routes `/images` to S3 and `/api` to EC2, terminates SSL, and integrates with AWS WAF to block SQL injection attacks based on payload inspection.
3. **Cloudflare Edge:** Cloudflare acts as a massive global Layer 7 reverse proxy. Because it operates at L7, it can read HTTP payloads to block malicious bots, cache specific images, and enforce rate limits based on specific API endpoints.
4. **Google Maglev:** Google's internal L4 load balancer. It uses consistent hashing for its connection tracking tables so that if a Maglev node crashes, only a fraction of the TCP connections need to be re-established, rather than dropping all global traffic.

## Advantages, Disadvantages, and Trade-offs

| Feature | Layer 4 (Transport) | Layer 7 (Application) |
| :--- | :--- | :--- |
| **Performance** | Extreme. Can handle millions of RPS. | Moderate. Parsing HTTP and TLS burns CPU. |
| **Routing Logic** | Dumb. Only IP and Port. | Smart. URL, Headers, Cookies, Methods. |
| **Security** | Basic. IP whitelisting/blacklisting. | Advanced. WAF, payload inspection, rate limiting. |
| **Backend Offload** | None. Backend handles TCP/TLS. | High. Multiplexing, TLS termination, caching. |
| **Protocol Support**| Any TCP/UDP (Databases, Games, IoT). | HTTP/HTTPS, gRPC, WebSockets, MQTT. |

**The Core Trade-off:** Intelligence costs CPU. Every time you ask a load balancer to "look inside" the packet, you drop its maximum throughput by an order of magnitude.

## Common Misconceptions

1. "Layer 4 is stateless." 
   False. TCP is a stateful protocol. An L4 LB must maintain a stateful connection tracking table (Conntrack) to map return packets to the correct client. (UDP L4 can be stateless, but TCP cannot).
2. "You should always use Layer 7 because it's smarter." 
   False. If you are ingesting 5 million raw telemetry events per second via TCP, an L7 LB will melt trying to parse them. You use L4 to blast the traffic to the ingestion servers.
3. "WebSockets are a different protocol." 
   False. A WebSocket starts as a standard Layer 7 HTTP GET request with an `Upgrade: websocket` header. The L7 LB must recognize this header, approve the upgrade, and then step back and act as a Layer 4 TCP proxy for the remainder of the persistent connection.
4. "L7 LBs can route encrypted traffic." 
   False. If you use TLS Pass-Through, the payload is encrypted. The L7 LB cannot read the URL path to route it. You must terminate TLS at the LB to route by URL.

## Industry Implementation

Modern cloud architectures use a **hybrid approach**. 
- **The Edge:** Traffic hits a Layer 7 LB (like Cloudflare or AWS ALB) for WAF protection, SSL termination, and smart routing. 
- **The Internal Network:** Traffic is passed to a Layer 4 LB (like AWS NLB or Kubernetes kube-proxy) to blast the traffic to the internal microservice pods with minimal latency.
- **The Database Layer:** Traffic hits a specialized Layer 4 proxy (like PgBouncer or ProxySQL) that understands the database wire protocol, pooling hundreds of app connections into a few database connections.

## AI/ML System Design Perspective

In AI infrastructure, the split between L4 and L7 is strictly defined by the data plane vs. the control plane:
- **Layer 7 for Inference Routing:** When a user queries an LLM, the API Gateway (L7 LB) reads the HTTP payload. It checks the `Authorization` header for quota limits, reads the `model: gpt-4` parameter, and routes the request specifically to the high-end GPU cluster. It also handles streaming the Server-Sent Events (SSE) back to the client.
- **Layer 4 for Training Data Ingestion:** When training a model, the GPUs must ingest terabytes of data from distributed storage (like S3 or HDFS). This is done via raw TCP streams. Putting an L7 LB in this path would destroy the I/O throughput. High-performance L4 LBs (or direct RDMA network fabrics) are used to maximize storage bandwidth.

## Revision Sheet

- **Layer 4 (Transport):** Routes by IP and Port. Fast, high throughput, low CPU. Cannot read payload. Requires Conntrack (TCP) or DSR.
- **Layer 7 (Application):** Routes by HTTP content (URL, headers). Slower, high CPU. Enables smart routing, WAF, and TLS termination.
- **TLS Termination:** Decrypting at the LB to save backend CPU and enable payload inspection.
- **HTTP/2 & gRPC Trap:** Multiplexed connections require L7 LBs to balance *per-stream*, not per-connection.
- **WebSockets:** Start as L7 HTTP Upgrade, then transition to L4 persistent TCP proxying.
- **DSR (Direct Server Return):** Bypasses the LB on the return trip to eliminate egress bottlenecks.
- **Rule of Thumb:** Use L7 at the edge for intelligence and security; use L4 internally for raw speed and database protocols.

# Topic 4: Health Checks, Failover, and Circuit Breaking

## Intuition First (The Why)
A resilient distributed system behaves like a modern power grid. The grid has three distinct defenses:
1. **Sensors** continuously measure voltage at every substation to detect a fault the moment it appears.
2. **Automatic transfer switches** reroute power from a failed substation to a healthy one, often so fast that lights only flicker.
3. **Circuit breakers** isolate a burning household so the fault cannot travel up the line and black out the entire city.

Distributed systems use the same three defenses under different names. **Health checks** are the sensors (detection). **Failover** is the transfer switch (rerouting). **Circuit breaking** is the breaker (containment). Most catastrophic outages are not caused by the initial failure; they are caused by one of these three defenses being missing, misconfigured, or too slow.

---

## Detailed Explanation

### The Three Questions Each Mechanism Answers
- **Health Check:** "Is this specific instance currently capable of serving traffic?" Answered by the load balancer or orchestrator about its backends.
- **Failover:** "Now that this instance, zone, or region is gone, where does its traffic and its responsibilities go?" Answered by the routing and promotion layer.
- **Circuit Breaker:** "Should I, the caller, keep sending requests to a dependency that is hurting me?" Answered by the client about its downstream service.

Confusing these three roles is the root of most resilience misconfigurations.

### Part 1: Health Checks (Detection)

**Active vs Passive vs Hybrid**
- **Active:** The load balancer sends synthetic probes on a schedule to a dedicated endpoint. Detects failure before users do, but costs bandwidth and can miss "gray" failures that only appear under real load.
- **Passive:** The load balancer observes real traffic: error rates, timeouts, reset connections. Zero probe overhead and catches load-dependent failures, but the first users absorb the errors.
- **Hybrid (production standard):** Active probes catch dead servers; passive observation (often called outlier detection or ejection) catches degraded servers.

**Probe Depth Hierarchy**
1. **Shallow (process-level):** Is the port open? Is the process alive? Cheap, never couples your fate to dependencies.
2. **Medium (application-level):** Does the app respond to a trivial request with 200 OK? Catches deadlocks and event-loop starvation.
3. **Deep (dependency-level):** Can the app reach its database, cache, and queue? Catches broken wiring, but couples your instance's fate to shared dependencies. If the database blips, every instance fails its deep probe simultaneously, and the load balancer ejects the entire fleet at once. This has caused total outages from partial failures.

**Endpoint Semantics (Kubernetes-style naming)**
- `/livez` (liveness): Shallow only. Answers "am I deadlocked?" Failure means restart the process.
- `/readyz` (readiness): Medium to deep. Answers "can I serve traffic right now?" Failure means remove from load balancer but keep the process alive.
- `/startupz` (startup): Allows slow bootstrapping (cache warming, model loading) without being killed by an impatient liveness probe.

**Tuning Parameters and Flapping**
Every active check has an interval, a timeout, a healthy threshold (consecutive successes to re-enter the pool), and an unhealthy threshold (consecutive failures to eject). Too aggressive (1s interval, 1 failure) causes **flapping**: a server is ejected and re-added repeatedly during minor GC pauses, churning connection pools and logs. Too passive (30s interval, 5 failures) means users absorb errors for over two minutes. Production defaults typically sit near: 5 to 10 second interval, 2 to 3 consecutive failures to eject, 1 to 2 successes to return.

**The Empty Pool Problem**
If health checks eject every backend (for example, because a deep probe fails during a shared database outage), what should the load balancer do?
- **Fail-closed:** Return errors to all users. Safe for correctness-critical systems.
- **Fail-open:** Ignore health state and spray traffic to all backends anyway, hoping some requests succeed. Used by some edge proxies for static content.
This policy must be a deliberate decision, not an accident of default configuration.

### Part 2: Failover (Rerouting)

**Scopes of Failover**
1. **Instance-level:** One server dies; the load balancer redistributes to siblings. Seconds.
2. **Zone-level (AZ):** One data center loses power; internal DNS or the service mesh shifts traffic to other zones. Seconds to minutes.
3. **Region-level:** An entire cloud region fails; GSLB/DNS failover shifts users to another continent. Minutes, bounded by DNS TTL.
4. **Primary-promotion-level:** A database primary dies; a replica is elected and promoted. Seconds to minutes, with potential data loss depending on replication mode.

**Active-Passive vs Active-Active**
- **Active-Passive:** A standby waits (warm) or must be built from scratch (cold). Simple, but the standby is idle cost, and cold standbies famously fail during real disasters because they were never exercised.
- **Active-Active:** All capacity serves traffic constantly; failover is just redistribution. Better economics and always-exercised paths, but requires stateless design or shared state, and requires that survivors have headroom to absorb the dead node's load.

**The Failover Time Budget**
Total user-visible outage equals: detection time + decision time + promotion time + warm-up time. Teams optimize detection but forget warm-up: a freshly promoted replica with cold caches and cold connection pools can be slower than the dead primary, causing a second wave of failures. Production failover plans include a ramp-up (slow start) for the promoted node.

**Capacity Is Part of Failover**
Failover that lands traffic on survivors already at 80% utilization does not restore service; it cascades the outage. Resilient fleets are sized N+1 or N+2 per zone, and failover drills verify that the surviving footprint can absorb the lost share at peak load.

**Split-Brain and Fencing**
During a network partition, both an old primary and a new primary may believe they own the data. Writes to both produce irreconcilable corruption. Prevention requires:
- **Quorum:** Promotion only by a majority of voters, so the minority partition cannot promote.
- **Fencing (STONITH or fencing tokens):** The old primary must be forcibly disabled, or its writes must be rejectable by storage via a monotonic fencing token (for example, an etcd lease epoch). A failover system without fencing is a data-corruption system.

### Part 3: Circuit Breaking (Containment)

**The Failure It Prevents**
Service A calls Service B. B slows to 15-second responses. A's worker threads block waiting. A's thread pool fills. A stops responding to its own callers. The failure has cascaded from B to A to A's users, without B ever crashing. This is a **cascading failure via resource exhaustion**, and timeouts alone only soften it.

**The State Machine, Precisely**
- **Closed:** Calls flow. A sliding window records outcomes. Two common window types: count-based (last N calls) and time-based (last T seconds, bucketed).
- **Open:** Triggered when a threshold crosses, typically an error-rate threshold (for example, 50% of the last 100 calls) and/or a slow-call-rate threshold (for example, 40% of calls exceeding 2 seconds). While open, calls fail immediately (or hit a fallback) without touching the network. This sheds load from B and frees A's threads.
- **Half-Open:** After a wait duration, a limited number of probe calls (not necessarily one; production breakers allow a small configurable concurrency) are permitted. If they succeed, the breaker closes, often with a gradual ramp. If they fail, the breaker reopens and the wait may grow exponentially.

**Companion Patterns (a breaker alone is incomplete)**
- **Timeouts:** Mandatory. A circuit breaker without a timeout waits forever to measure failures and never trips.
- **Retries with backoff and jitter, plus a retry budget:** Cap retries at a small percentage of total traffic (for example, 10%) so retries cannot amplify load.
- **Bulkheads:** Isolate resources per dependency (separate thread or connection pools) so one slow dependency cannot consume all of A's capacity. Named after ship compartments.
- **Fallbacks:** Define what the user gets when the breaker is open: a cached value, a default, a degraded experience, or a clean fast error. A breaker without a fallback just converts slow failures into fast failures.
- **Hedging:** For latency-sensitive reads, send a second request to a replica if the first is slow, and cancel the loser. Use sparingly; hedging doubles load.

## Real-World Examples

1. **Kubernetes probe misconfiguration outage pattern:** A team pointed liveness probes at an endpoint that queried the database. During a database slowdown, every pod failed liveness simultaneously, Kubernetes restarted the entire fleet, the restart storm hit the struggling database harder, and a partial degradation became a total outage. The fix: liveness stays shallow; dependency awareness belongs in readiness.
2. **Envoy outlier detection:** In Istio and Linkerd meshes, Envoy ejects hosts passively based on observed 5xx rates and consecutive gateway failures, with configurable ejection duration and max ejection percentage (a safety valve that prevents ejecting more than, say, 50% of the pool no matter how bad things look).
3. **AWS multi-layer failover:** Elastic Load Balancing target health checks handle instance failover in seconds; Multi-AZ RDS handles primary promotion in roughly one to two minutes; Route 53 health-checked failover records handle region-level shifts, bounded by the TTL you chose.
4. **Netflix GameDay and chaos engineering:** Netflix deliberately killed services and zones in production to prove that failover and circuit breakers actually worked, famously discovering that fallbacks had silently rotted. Resilience mechanisms decay if never exercised.

## Internal Working: Mechanics Worth Knowing

1. **Probe sourcing:** Load balancer health probes arrive from known source IP ranges; backends must allow them through security groups, and probes should hit a lightweight endpoint served by the same event loop as real traffic (otherwise a wedged event loop passes health checks while dropping users).
2. **Sliding window implementation:** Count-based windows are ring buffers of boolean outcomes; time-based windows bucket outcomes into, for example, ten 1-second buckets and drop the oldest. Time-based windows behave better under variable traffic; count-based windows behave better under tiny traffic volumes.
3. **Half-open concurrency:** Allowing exactly one probe call can take many seconds to validate a slow dependency; production breakers permit a small configurable number of concurrent probes and close on a success-rate threshold, not a single success.
4. **Leases and epochs for fencing:** Systems like etcd grant the leader a lease with a TTL and a monotonic revision. Storage layers can reject writes carrying stale revisions, making split-brain corruption impossible even if the old leader is still alive and unaware.
5. **Interaction with connection draining:** Ejection via health check should honor draining for in-flight requests where possible; hard ejection (drop everything) is reserved for nodes that are truly unreachable.

## Advantages, Disadvantages, and Trade-offs

- **Detection speed vs flapping:** Faster detection means users see fewer errors, but aggressive thresholds eject healthy nodes during GC pauses and traffic bursts.
- **Probe depth vs coupled fate:** Deep probes catch more real breakage but turn a shared dependency blip into a fleet-wide ejection event.
- **Failover automation vs false positives:** Automated promotion is fast but can promote during a transient partition, causing unnecessary churn; manual promotion is safe but slow. Quorum plus fencing makes automation trustworthy.
- **Breaker sensitivity vs degraded availability:** A breaker that trips too easily denies users a service that was merely slow; a breaker that never trips burns threads until total collapse. Thresholds must come from measured latency baselines, not guesses.
- **Fail-open vs fail-closed on empty pools:** Fail-open preserves partial service at the risk of amplifying load on sick nodes; fail-closed preserves correctness at the cost of a total stop.

---

## Common Misconceptions

1. "A 200 OK from the health endpoint means the service can serve users." False. It may be unwarmed, missing a dependency, or its event loop may be healthy while its database pool is exhausted. That is exactly why readiness exists separately from liveness.
2. "Deeper health checks are strictly better." False. Deep checks couple instance fate to shared dependencies and can eject an entire fleet during a partial failure.
3. "Failover is instant." False. Detection, decision, promotion, and warm-up all consume time, and survivors must have headroom or failover becomes a cascade.
4. "Circuit breakers and retries are the same resilience tool." False. Retries add load to a struggling dependency; breakers remove load. They must be configured together with a retry budget.
5. "An open circuit means the downstream service is down." False. It may be slow (slow-call threshold), or your own client pool may be saturated. The breaker reports harm to you, not truth about them.
6. "More frequent health checks always improve availability." False. Probe storms consume CPU on backends and increase flapping; detection speed has a cost curve.

## AI/ML System Design Perspective

- **Training resilience:** Distributed training on thousands of GPUs fails constantly at node scale. Clusters run active hardware health checks (ECC memory errors, NVLink integrity, NVIDIA XID codes) and use elastic training: on a detected bad node, the job checkpoints, the ring topology is rebuilt excluding the sick node, and training resumes. Failover here is measured in minutes and is budgeted into job scheduling.
- **Serving resilience:** Inference fleets use latency-based outlier ejection because a GPU can be "alive" yet catastrophically slow (thermal throttling, memory fragmentation). Circuit breakers trip on slow-call rates and route to fallback model pools (smaller models) so users receive a degraded answer instead of a timeout.
- **Statefulness cost:** Failing over an in-flight LLM session loses the KV cache, so production routers either accept recomputation or replicate session state, a direct application of the stateful failover costs studied in earlier topics.
- **Spot capacity failover:** Training on preemptible GPUs requires constant checkpointing and the ability to relaunch on different capacity, making failover a routine operational path rather than an emergency.

## Revision Sheet

- **Three defenses:** Detection (health checks), rerouting (failover), containment (circuit breaking).
- **Active checks:** synthetic probes; catch death before users do. **Passive checks:** observe real traffic; catch gray failure.
- **Probe depths:** shallow (process), medium (app), deep (dependencies). Deep checks couple fate; use carefully.
- **Endpoints:** /livez shallow and restart-on-fail; /readyz dependency-aware and eject-on-fail; /startupz for slow boots.
- **Flapping:** tune interval and thresholds; ejection and re-admission both need consecutive counts.
- **Empty pool policy:** fail-open vs fail-closed must be deliberate; cap max ejection percentage.
- **Failover scopes:** instance, zone, region, primary promotion. Budget = detect + decide + promote + warm up.
- **Split-brain prevention:** quorum election plus fencing (STONITH or monotonic tokens/leases).
- **Circuit breaker states:** closed, open, half-open; sliding windows; error-rate and slow-call-rate thresholds.
- **Companions:** timeouts (mandatory), retry budget with backoff and jitter, bulkheads, fallbacks, hedging.
- **Capacity:** failover without headroom is a cascade; size N+1 or N+2 and drill it.

# Topic 5: Sticky Sessions and Session Persistence

## Intuition First (The Why)
Imagine a gym with three locker rooms. When you join, the attendant assigns you a locker in Room B and writes your membership details on a card stored inside that locker. From now on, the receptionist must always send you to Room B, because your belongings only exist there. If Room B floods and closes, your membership is effectively gone. This forced routing is a **sticky session**.

Now imagine two better gyms. In the first, all lockers are moved to a central vault underground; any room's attendant can fetch your belongings, so you can enter through any door. In the second, you carry a sealed, tamper-proof claim ticket that describes exactly what you own; no storage is needed at all, and any attendant can verify your ticket on the spot.

These three designs are exactly the three strategies for handling user state behind a load balancer: pin the user to one server (stickiness), externalize the state to a shared store (central vault), or make the client carry a verifiable token (claim ticket). Understanding when each is legitimate, and why the first one is usually a debt rather than a solution, is the core of this topic.

---

## Detailed Explanation

### The Root Problem: HTTP Is Stateless
As established earlier in the roadmap, HTTP carries no memory between requests. Yet applications need continuity: who is logged in, what is in the cart, which CSRF token is valid, which language the user chose. The standard mechanism is a **session**: a server-side record keyed by a random **session ID**, with the ID transported to the client in a cookie and returned on every request.

The moment you store that record in a single server's memory, you have created a routing constraint: requests carrying that session ID must reach that specific server, or the user appears logged out. **Session persistence** (also called **session affinity** or **sticky sessions**) is the load balancer feature that honors this constraint by routing all requests from a given client to the same backend server.

### Mechanisms for Implementing Stickiness

**1. Source IP Hashing**
The load balancer hashes the client IP to pick a server. No cookies involved.
- Weaknesses: CGNAT and corporate proxies collapse thousands of users into one IP, creating hotspots; mobile clients change IPs constantly, breaking stickiness; adding or removing servers remaps most clients (mod-N problem).

**2. Load-Balancer-Inserted Cookie**
On the first request (no cookie present), the LB picks a server using its normal algorithm, then sets its own cookie encoding the chosen target (for example, an encrypted target identifier plus an expiry). Every subsequent request carries that cookie, and the LB routes directly to the encoded target.
- Examples: AWS ALB duration-based stickiness cookie; HAProxy `cookie ... insert`; nginx Plus sticky cookie.
- Strengths: precise per-client stickiness, unaffected by CGNAT.
- Weaknesses: only works for cookie-capable clients (browsers); pure API clients must store and return the cookie manually; if the LB fleet restarts or config changes, encoded targets must remain decodable (shared secrets or deterministic encoding required).

**3. Application Cookie Hashing**
The LB reads the application's own session cookie (for example, `SESSIONID`) and hashes its value to select a server. HAProxy supports `prefix` and `rewrite` modes for this.
- Strengths: stickiness aligns with real session boundaries, not arbitrary IPs; survives client IP changes.
- Weaknesses: the LB must parse application cookies, coupling infrastructure to application naming; session ID entropy must be high or hashing clusters users.

**4. Custom Header or Tenant Hashing**
For API traffic, hash a stable identifier the client sends, such as a tenant ID or user ID header. This is application-aware affinity and is common in multi-tenant SaaS where per-tenant caches matter.

**5. Consistent Hashing for Affinity (Soft Stickiness)**
Instead of mod-N, place servers on a hash ring (ring hash or Maglev, as in Envoy). Hash the session or client key to the ring; the nearest server owns it. When the fleet changes, only a small fraction of keys remap.
- This converts stickiness from a brittle promise into a best-effort affinity that degrades gracefully, and it is the bridge to Topic 10.

### Where Stickiness Is Genuinely Needed
1. **Legacy in-memory sessions:** Java HttpSession, PHP sessions, or any monolith that never externalized state.
2. **Local disk state:** uploads staged to local filesystem, local temp files, local compiled caches.
3. **Long-lived connections:** WebSockets and SSE are pinned by physics once the TCP connection exists; stickiness matters for the handshake and for reconnection behavior.
4. **Performance locality:** a warm per-user cache on one server can justify best-effort affinity even when correctness does not require it.
5. **Migration windows:** during a refactor toward statelessness, stickiness is the temporary safety net.

### The True Costs of Sticky Sessions
1. **Load imbalance:** a few heavy users (whales, crawlers, large tenants) pin disproportionate load to single servers while siblings idle. Stickiness fights your load balancer's primary job.
2. **Broken failover:** the pinned server dies and the session dies with it. Users get logged out mid-checkout. Stickiness directly trades away the high availability you built the load balancer for.
3. **Deployment friction:** rolling updates must drain pinned connections; during deploys, some users hit old-version servers and some hit new, producing version skew bugs that only affect "some users sometimes."
4. **Scaling inefficiency:** adding capacity does not help existing sessions until they expire or reconnect; scaling in kills sessions outright.
5. **Operational opacity:** debugging "why is this one user slow" becomes "which server owns them and what is special about it," which slows incident response.

### The Three Modern Alternatives

**Alternative 1: Externalized Shared Session Store (the central vault)**
Move session records out of server memory into Redis, Memcached, or a database table. Any server can serve any request; stickiness is deleted from the configuration.
Design details that make it production-grade:
- Session ID: high-entropy random value (for example, 128 bits or more), transported in a cookie flagged `HttpOnly`, `Secure`, and `SameSite`.
- Storage: key = session ID, value = serialized session object, with a TTL.
- Sliding expiration: refresh the TTL on each access so active users stay logged in while idle sessions die.
- Regenerate the session ID at privilege changes (login) to defeat session fixation.
- Keep sessions small; they are read and written on every request.

**Alternative 2: Stateless Signed Tokens (the claim ticket)**
Issue a JWT (or similar) signed by the server. The token carries the claims (user ID, roles, expiry). Any server verifies the signature cryptographically without storage.
- Strengths: zero shared state, trivially horizontal, works across domains and services.
- Weaknesses: revocation is hard (tokens live until expiry, so use short lifetimes plus refresh tokens, or maintain a denylist, which reintroduces state); tokens bloat every request header; sensitive data must never sit in a merely signed (readable) payload without encryption.

**Alternative 3: Data-Layer Affinity (stickiness moved down the stack)**
Instead of pinning compute, shard user state by user ID so that all of a user's data lives in one shard (Topic 19 of Chapter 1). Any compute node can serve any user; the "locality" lives where the data is durable and replicated. This is the architecture of large social networks.

### The Production Migration Pattern: From Sticky to Stateless Without Downtime
Refactoring a legacy sticky-session monolith is a classic senior engineering project. The safe sequence is dual-write:
1. **Phase 1 - Write-through:** Keep stickiness enabled. The app writes every session change to both local memory and Redis.
2. **Phase 2 - Read-from-shared-first:** The app reads from Redis first and falls back to local memory on miss (backfilling Redis). Stickiness still on; behavior unchanged.
3. **Phase 3 - Canary the statelessness:** Disable stickiness for a small percentage of traffic. Monitor session-miss rates, unexpected logouts, and latency. Fix serialization bugs found here.
4. **Phase 4 - Cut over:** Disable stickiness fully, then delete the local session code path and the stickiness configuration.
Each phase is independently rollback-able, which is what makes this pattern trustworthy.

## Real-World Examples

1. **AWS ALB stickiness:** Target groups support duration-based stickiness via an LB-inserted cookie (configurable duration, defaulting to one day). It exists precisely for legacy applications, and AWS documentation itself steers new designs toward stateless targets.
2. **HAProxy cookie modes:** `insert` (LB adds its own cookie), `prefix` (LB prefixes the app cookie with the server name), and `rewrite` (LB rewrites the app's cookie). These three modes map exactly to the mechanisms described above and appear in countless production configs.
3. **WebSocket chat fleets:** A chat server holds each user's socket connection (pinned by physics). To let users on different servers message each other, the fleet shares a Redis Pub/Sub channel or message bus. On reconnect after a server death, the client re-authenticates and the new server rebuilds presence from the shared store. Stickiness was never the solution; shared state was.
4. **Kubernetes clientIP affinity:** Kubernetes Services offer `sessionAffinity: ClientIP`, and Ingress controllers offer cookie affinity annotations. Both are documented as legacy-compatibility tools; cloud-native guidance is to externalize state and leave affinity off.

## Internal Working: Mechanics Worth Knowing

1. **Cookie insertion flow, step by step:** First request arrives without a stickiness cookie. The LB selects a target with its normal algorithm. The LB encrypts or hashes the target identifier with a fleet-shared key and sets it as a cookie with an expiry. Subsequent requests decrypt the cookie and route directly. If decryption fails or the target is gone, the LB falls back to normal selection and re-issues the cookie.
2. **Multi-LB consistency:** If several LB instances serve the same VIP, they must share the cookie key or use deterministic encoding (consistent hashing), or a cookie issued by LB-1 will be undecodable by LB-2, silently breaking stickiness on every LB failover.
3. **Sliding TTL in Redis:** On each request, the app issues `EXPIRE session:<id> <seconds>` after a successful read. Without this, active users get logged out at the original TTL; with it, idle sessions still die on schedule.
4. **Session size economics:** The session is fetched and written on every request. A 10KB session blob at 5,000 requests per second is 100MB per second of Redis traffic. Keep sessions to identifiers and flags; put bulk data elsewhere.
5. **Stickiness versus connection reuse:** HTTP Keep-Alive already gives accidental micro-stickiness (a persistent connection stays on one server). This is harmless and desirable. True session stickiness becomes dangerous only when correctness depends on it.

## Advantages, Disadvantages, and Trade-offs

- **Stickiness advantages:** zero refactoring for legacy apps; preserves local cache warmth; simple to enable with one config line.
- **Stickiness disadvantages:** imbalance, lost sessions on failover, deployment skew, poor scaling behavior, incident-debugging opacity.
- **Shared store advantages:** true statelessness, instant failover, even load, easy horizontal scaling.
- **Shared store disadvantages:** one extra network hop per request; a new critical dependency (the store itself must be highly available and replicated); serialization and schema-evolution burden.
- **Token advantages:** no storage, no extra hop, excellent across service boundaries.
- **Token disadvantages:** revocation latency, header bloat, key-management and claim-hygiene responsibilities.
- **The governing trade-off:** locality versus availability. Stickiness buys locality by mortgaging availability. Externalized state buys availability by paying a small, predictable latency tax.

## Common Misconceptions

1. "Sticky sessions solve the stateful-server problem." False. They postpone it and pay for it with availability. The problem is solved only when state leaves the server or the server's death stops mattering.
2. "JWT makes my system completely stateless." False in practice. Refresh tokens, revocation lists, rate-limit counters, and audit state still live server-side. JWT removes session storage, not all state.
3. "ip_hash is a fine stickiness mechanism." False in production. CGNAT hotspots, mobile IP churn, and mod-N remapping make it the weakest option.
4. "A sticky cookie guarantees the same server forever." False. Cookies expire, fleets change, LBs fail over. Stickiness is a best-effort hint with an expiry date.
5. "WebSockets require sticky sessions at the load balancer." False. An established TCP connection is already pinned. What you actually need is shared state for reconnection and cross-node fanout.
6. "Externalizing sessions to Redis adds a dangerous single point of failure." Only if deployed naively. A replicated Redis cluster with sentinel or cluster-mode failover is typically more available than the fleet of app servers it serves.

The default production pattern across the industry is: stateless application servers plus a replicated Redis (or ElastiCache / MemoryDB) session store with sliding TTLs, or short-lived JWTs with refresh tokens for API-first products. ## AI/ML System Design Perspective

Stickiness is experiencing a careful, performance-driven revival in LLM serving, under a new name: **KV-cache affinity**.
- In multi-turn conversations, the worker that generated turn N already holds the prompt and history key-value cache. Routing turn N+1 to that same worker skips recomputation, cutting time-to-first-token and GPU cost dramatically.
- Production routers therefore implement **soft affinity**: prefer the worker holding the prefix cache (consistent hashing over session or prefix hash), but let queue depth and memory pressure veto the choice. Affinity is a hint; load is a veto. This is the exact lesson of this topic applied correctly: locality for performance, never for correctness.
- The durable source of truth, the conversation history itself, still lives in an external store (database or object storage), because workers die and KV caches evaporate. When affinity fails, the fallback is recomputation from history, exactly like a session-miss fallback in web architecture.
- Training and fine-tuning jobs remain genuinely stateful (optimizer state, checkpoints), and their "stickiness" is handled by schedulers with checkpoint-restart, not by load balancers.

- **Session:** server-side state keyed by a random ID carried in a cookie; HTTP itself is stateless.

- **Legitimate uses:** legacy in-memory sessions, local disk state, long-lived connections, cache warmth, migration windows.

# Topic 6: Load Balancer Redundancy: Eliminating the Single Point of Failure

## Intuition First (The Why)
Imagine a fortress with impenetrable walls, redundant water supplies, and three backup generators, but exactly one drawbridge. It does not matter how strong the walls are or how many generators hum inside: whoever controls or destroys that single drawbridge controls the entire fortress.

A load balancer is the drawbridge of your architecture. Every request crosses it. You can replicate databases, add read replicas, and build active-active server fleets, but if a single load balancer instance sits in front of all of it, your system's availability is capped by that one machine's reliability. Making the load balancing layer itself survivable is therefore not an optimization; it is the prerequisite that makes every other redundancy investment meaningful.

---

## Detailed Explanation

### The Reliability Math That Forces This Topic
Components in a request path behave like a series circuit: total availability is the product of individual availabilities.
- A load balancer at 99.99% (about 52 minutes of downtime per year) in front of a backend fleet at 99.99% yields roughly 99.98% end-to-end (about 105 minutes per year). The single LB quietly doubles your outage budget.
- Placing two independent load balancers in parallel changes the math: unavailability becomes (1 - A) squared. Two 99.99% members theoretically yield about 99.9999% (roughly 31 seconds per year).
- The catch: independence is an assumption, not a fact. Two LBs sharing a power feed, a top-of-rack switch, a config pipeline, or a software version are not independent. Common-cause failure is what turns "redundant pairs" into simultaneous outages, and defeating it is the real work of this topic.

### Pattern 1: Active-Passive Pair with a Floating Virtual IP
The classic on-premises design. Two load balancers (for example, HAProxy or LVS plus keepalived) share a Virtual IP (VIP) that only the active member owns.
- A heartbeat protocol (VRRP or CARP) sends advertisements between the pair, typically every second, over a dedicated link.
- When the passive member misses advertisements beyond a dead interval, it promotes itself: it assigns the VIP to its own interface and broadcasts a **gratuitous ARP** so the upstream switch relearns which MAC address now owns the VIP.
- Failover typically completes in one to three seconds. Clients experience a brief blip; established TCP connections usually reset unless state is synchronized.
- **Split-brain risk:** if only the heartbeat link fails (both members alive), both promote and both answer for the VIP, corrupting traffic. Mitigations: dual heartbeat paths (network plus crossover or serial link), quorum via a third witness node, and upstream switch configurations that detect duplicate VIP ownership.

### Pattern 2: Active-Active with DNS Distribution
Multiple load balancers, each with its own real IP, all listed in one DNS A record (round robin).
- Advantage: all capacity serves traffic; no idle standby cost.
- Fatal weakness: DNS is cached. When LB-1 dies, resolvers and clients keep using its IP until TTL expiry, and many clients do not retry the other A records properly. Failover time is bounded by TTL (minutes), not by health (seconds).
- Mitigations: very low TTLs, health-checked DNS (Route 53 failover records), and clients with robust retry-across-addresses logic. Even then, this pattern is a compromise, not a solution.

### Pattern 3: Active-Active with ECMP and BGP Anycast
The internet-scale design used by CDNs and edge networks.
- Every load balancer instance announces the same VIP prefix via BGP to the upstream router.
- The router installs multiple equal-cost next hops and spreads traffic using **ECMP**, hashing each flow's 5-tuple (source IP, source port, destination IP, destination port, protocol) so that all packets of one TCP connection take the same path.
- When an LB dies, its BGP session drops, the route withdraws, and the router rehashes within seconds. Only the flows hashed to the dead member reset; everyone else is untouched.
- Anycast extends this geographically: the same VIP is announced from many data centers, and BGP topology routes each user to the nearest healthy one.
- Costs: you must operate routing (ASNs, BGP sessions, prefix management), and member changes cause flow repolarization (some flows remap), which is the mod-N problem in router form.

### Pattern 4: Managed Cloud Load Balancers
AWS ALB/NLB, GCP Load Balancing, and Azure Load Balancer are themselves distributed fleets spread across availability zones, with redundant control planes and data planes. You inherit their redundancy instead of building it.
- What you still own: regional failure (a cloud region's LB control plane can degrade), capacity limits, and cross-region failover design (Route 53 health-checked failover, Global Accelerator, or multi-region active-active).
- The mental shift: with managed LBs, redundancy design moves up one layer, from boxes to regions and routing policies.

### Pattern 5: Distributed Client-Side Balancing (Service Mesh)
Eliminate the central drawbridge entirely. In a service mesh, every service instance runs a sidecar proxy (Envoy) that performs load balancing per request using endpoint lists from a control plane.
- The SPOF dissolves: there is no single box, only per-call decisions with retries.
- A new SPOF candidate appears: the control plane (endpoint discovery, config). The industry answer is **fail-static data planes**: if the control plane dies, sidecars keep serving with their last-known good configuration. Losing the ability to change routing is an incident; losing the ability to route at all is an outage, and fail-static refuses the latter.

### What State Must Survive LB Failover
An L4 load balancer holds connection tracking state; an L7 balancer holds TLS session material, stickiness secrets, health-check views, and configuration. Two philosophies exist:
1. **State-synchronized failover:** replicate conntrack entries between the pair (for example, conntrackd with keepalived) so established connections survive. Complex, adds latency and bandwidth, and rarely perfect.
2. **Drop-and-reconnect failover:** accept that in-flight connections die; clients retry; idempotency keys and reconnect logic absorb the blip. Simple, honest, and the industry default for HTTP workloads.
Long-lived sessions (WebSockets, streaming, trading sockets) force the decision into the open: either synchronize state, or design application-level session resumption so a reconnect is cheap and lossless.

1. **keepalived plus HAProxy or LVS:** The canonical on-premises pair. VRRP advertisements, VIP failover, and optional conntrack synchronization. Thousands of production clusters run exactly this.
2. **Cloudflare and Google edge:** Anycast VIPs announced via BGP from hundreds of locations. A data center failure withdraws routes; global traffic reconverges in seconds without DNS involvement. Google's Maglev additionally uses consistent hashing for its connection tables so that member changes disturb only a fraction of flows.
3. **Facebook, October 2021:** A control-plane and BGP-level failure withdrew the company's routes from the internet, making its edge unreachable worldwide for hours. The lesson etched into industry practice: redundancy must cover routing and control planes, not just servers and LB boxes.
4. **Kubernetes:** kube-proxy runs on every node (distributed L4), Ingress controllers run as multiple replicas with pod anti-affinity across zones, and the control plane (etcd-backed) is quorum-replicated. Data planes continue forwarding during control-plane degradation.

---

## Internal Working: Mechanics Worth Knowing

1. **Gratuitous ARP:** After VIP takeover, the new active LB broadcasts an ARP announcement mapping the VIP to its own MAC. Without it, the upstream switch keeps forwarding to the dead member's MAC until its ARP cache ages out, stretching a one-second failover into minutes.
2. **VRRP tuning:** Advertisement interval and skew define detection speed versus false positives on congested heartbeat links. Production configs pair fast intervals with a witness or dual paths rather than simply lowering thresholds.
3. **ECMP flow consistency:** The router hash must cover the full 5-tuple so packets of one TCP flow never take different paths (out-of-order packets destroy TCP throughput). Member addition or removal repolarizes a subset of flows; consistent-hashing variants reduce but do not eliminate this.
4. **Conntrack memory as the real ceiling:** An L4 LB's scaling limit is usually the connection tracking table in RAM, not CPU. Redundancy planning must size the survivor's table for full traffic, not half.
5. **Config distribution is part of redundancy:** An Envoy or HAProxy fleet is only as redundant as its config pipeline. xDS control planes push config incrementally; a push that crashes every member simultaneously defeats all box-level redundancy (see misconceptions).

---

## Advantages, Disadvantages, and Trade-offs

- **Active-passive:** simple mental model, one VIP, predictable failover; but idle capacity cost, failover blip, and split-brain engineering burden.
- **Active-active DNS:** uses all capacity, trivial to configure; but failover bounded by TTL and client retry behavior; weakest detection story.
- **ECMP/BGP anycast:** second-scale convergence, full capacity use, geographic extension; but routing expertise required, flow repolarization on change, harder debugging.
- **Managed cloud LB:** zero box-level operations, AZ-level redundancy included; but regional blast radius remains yours, and deep tuning is limited.
- **Mesh/client-side:** no central SPOF, per-call resilience; but every client must be mesh-aware, and the control plane needs quorum replication plus fail-static guarantees.
- **State sync versus drop:** sync preserves long sessions at high complexity; drop is simple and honest but requires application-level reconnect design.

---

## Common Misconceptions

1. "Two load balancers in a pair means high availability." False if they share a power feed, rack switch, config pipeline stage, or software version. Redundancy is about independence, not count.
2. "Our cloud load balancer never fails, so this topic does not apply." Regional control-plane incidents happen. Critical workloads still need cross-region routing failover; the drawbridge moved, it did not disappear.
3. "DNS round robin across two LBs gives fast failover." Cached records keep sending clients to the dead IP for the full TTL, and many clients never try the second address. Detection is fast; recovery is not.
4. "Connection state must always survive failover." For most HTTP traffic, drop-and-reconnect with idempotency is cheaper and more reliable than state synchronization. Sync is a targeted tool for long-lived critical sessions.
5. "Redundancy protects against bad configuration." False. A config pushed to all members at once takes down every member at once. Redundancy defends against hardware death; change management defends against yourself.
6. "The passive member is always ready." Cold standbys rot: stale configs, untested kernels, drifted certificates. Production pairs exercise failover on schedule (chaos drills) or run active-active so both paths stay warm.

# Topic 7: SSL/TLS Termination and Offloading

## Intuition First (The Why)
Imagine an international airport where every arriving passenger speaks a different language and carries a sealed, encrypted diplomatic pouch. Inside the terminal, all staff speak one common language and work with open documents.

Somewhere between the gate and the terminal, someone must open each pouch, verify the seals, translate the contents, and reissue them as internal paperwork. Doing this at every single office inside the terminal would be absurdly wasteful. Instead, the airport does it once, at a specialized customs desk right at the gate, staffed with experts and seal-verification hardware.

TLS termination is that customs desk. The load balancer (or edge proxy) performs the expensive cryptographic work once, at the boundary, so that everything inside your network can work in the fast, plain, inspectable internal format. Where you place that desk, and whether some pouches must stay sealed all the way to their final destination, is one of the most consequential security and performance decisions in an architecture.

---

## Detailed Explanation

### What TLS Actually Provides
TLS (Transport Layer Security, the successor to SSL) delivers three guarantees for data in transit:
1. **Confidentiality:** payload encrypted so eavesdroppers cannot read it.
2. **Integrity:** tampering is detectable via authenticated encryption (for example, AES-GCM).
3. **Authenticity:** certificates prove the server (and optionally the client) is who it claims.

Establishing these guarantees costs a handshake: asymmetric cryptography (key exchange, signature verification), certificate chain validation, and negotiated session keys. After the handshake, bulk data uses cheap symmetric encryption. This asymmetry of cost, expensive handshake and cheap bulk transfer, is the economic foundation of termination and offloading.

### The Three Deployment Modes

**Mode 1: TLS Termination (Offloading)**
The load balancer terminates the client's TLS connection, decrypts the traffic, and forwards plain HTTP to backends over the internal network.
- The LB holds the certificates and private keys.
- Backends see ordinary HTTP and spend zero CPU on cryptography.
- The LB can read headers and paths, enabling L7 routing, WAF inspection, rate limiting, and logging.

**Mode 2: TLS Re-encryption (Bridging)**
The LB terminates the client TLS connection, then opens a second, independent TLS connection to the backend.
- Traffic is encrypted on both segments with two separate handshakes.
- The LB still sees plaintext in memory, so L7 features remain available.
- Internal hops are protected against network-level eavesdropping, satisfying stricter compliance postures without giving up edge intelligence.

**Mode 3: TLS Pass-Through**
The LB forwards encrypted bytes without decrypting. The backend holds the certificate and performs the handshake and decryption.
- True end-to-end encryption; the LB is blind to content.
- All L7 capabilities at the LB are lost (no URL routing, no WAF on payload, no header manipulation).
- Certificates must be deployed and rotated on every backend, which is an operational tax.

### Why Termination at the Load Balancer Wins by Default
1. **Certificate centralization:** one place to store keys, renew certificates, automate ACME issuance, monitor expiry, and enforce policy. Rotating a certificate touches one fleet, not five hundred backends.
2. **Backend CPU reclaimed:** handshakes are asymmetric-crypto-heavy. Offloading them frees backend cores for application logic, which is where your money is actually made.
3. **Hardware acceleration concentration:** AES-NI instructions, crypto co-processors, and TLS-aware NICs are installed once at the edge fleet instead of everywhere.
4. **Policy consistency:** minimum TLS versions, cipher suites, HSTS, and OCSP stapling are enforced at one choke point. Backends cannot drift into weak configurations.
5. **Protocol translation:** the LB can speak TLS 1.3 and HTTP/2 to the world while speaking plain HTTP/1.1 to legacy backends, modernizing the edge without rewriting the core.
6. **Connection economics:** the LB absorbs slow clients, holds thousands of TLS sessions with resumption tickets, and multiplexes them over a small pool of warm backend connections.

### The Costs and Risks You Accept with Termination
1. **Plaintext inside the perimeter:** everything between LB and backend is readable by anything on that network path. Mitigations: strictly private networks, VPC isolation, security groups that admit only the LB, re-encryption for sensitive paths, or internal mTLS.
2. **The LB becomes a crypto choke point:** handshake storms (for example, after a cache of session tickets is lost) can saturate LB CPU. Sizing must account for handshake rate, not just request rate.
3. **Compliance boundaries:** regimes such as PCI-DSS and HIPAA require encryption in transit across untrusted segments. If the internal network is not formally scoped as trusted, termination with plaintext internals fails audit; re-encryption or pass-through becomes mandatory.
4. **Trust concentration:** the edge now holds every private key. Key management (HSM or KMS backing, least-privilege access, rotation) becomes a tier-1 security concern.

---

## Mental Model and Analogy
- **Termination:** the customs desk at the gate. Pouches are opened once, verified by experts, and become internal paperwork. Fastest internal operations, but everything inside is open to anyone standing in the terminal.
- **Re-encryption:** customs opens the pouch, copies the contents into a new sealed internal pouch, and the receiving office opens that one. Two seals, two verifications, full inspection capability in between.
- **Pass-through:** the diplomatic pouch travels sealed from origin to final office. Maximum confidentiality, zero inspection, and every office must keep its own seal-verification kit current.

## Real-World Examples

1. **CDN edges (Cloudflare, Akamai, Fastly):** terminate TLS at the nearest point of presence, serve cached content without ever contacting the origin, and re-encrypt origin pulls. Users get a 1-RTT handshake with a nearby edge instead of a 2-RTT handshake with a distant origin.
2. **AWS ALB with ACM:** certificates live in AWS Certificate Manager with automated renewal; the ALB terminates TLS, injects X-Forwarded headers, and speaks HTTP/2 to clients while forwarding HTTP/1.1 to targets. NLB offers TLS pass-through (or TLS listeners with termination) for regimes that need it.
3. **Service meshes (Istio, Linkerd):** the opposite extreme, applied deliberately: mTLS everywhere, with every hop terminated at sidecar proxies. Zero-trust replaces perimeter-trust; the CPU cost is accepted because AES-NI makes bulk encryption cheap and handshakes are amortized over long-lived connections.
4. **Certificate expiry outages:** multiple publicized incidents (telecom and cloud providers among them) trace to expired certificates on distributed fleets that lacked centralized automation and expiry alerting. Centralized termination plus ACME automation plus expiry monitoring is the direct antidote.

---

## Internal Working: Mechanics Worth Knowing

1. **SNI (Server Name Indication):** the client includes the target hostname inside the ClientHello, before any certificate is sent. This lets one LB IP serve thousands of domains with the correct certificate per connection. SNI is what makes multi-tenant edges and mass custom-domain SaaS possible. (Encrypted ClientHello is emerging to hide the hostname from passive observers.)
2. **Session resumption economics:** TLS session tickets (stateless) let returning clients skip the full handshake. Ticket encryption keys must be shared across the LB fleet and rotated on schedule; otherwise, after an LB failover, resumption silently collapses into full handshakes and CPU spikes (this pairs directly with Topic 6).
3. **0-RTT caution:** TLS 1.3 early data saves a round trip but is replayable by an attacker who captures it. Only idempotent requests (safe GETs) may use 0-RTT; never payments, never state changes.
4. **Header injection discipline:** after termination, the true client IP and original scheme exist only in X-Forwarded-For, X-Forwarded-Proto, and X-Forwarded-Port. The edge must overwrite client-supplied values, not append to them, and network ACLs must guarantee the LB is the only path to backends, or these headers become spoofable inputs.
5. **Zero-downtime certificate rotation:** production LBs hot-reload certificates (new SNI context loaded, old drained) so renewal never drops connections. Automation (ACME, cert-manager) plus canary deployment of new certs plus expiry alerting at 30/14/7 days is the standard lifecycle.
6. **mTLS and identity:** with mutual TLS, clients present certificates too. Edges can validate client certs and forward verified identity as internal headers, or re-encrypt with internal mTLS so every hop authenticates every peer. This is the foundation of zero-trust service meshes.
7. **Where the CPU actually goes:** handshake cost is dominated by asymmetric operations (signature and key exchange); bulk record encryption with AES-GCM on AES-NI hardware is near line-rate. Therefore handshake rate, connection churn, and resumption hit ratio are the metrics that size a termination fleet, not megabits per second.

## Advantages, Disadvantages, and Trade-offs

| Dimension | Termination | Re-encryption | Pass-through |
| :--- | :--- | :--- | :--- |
| Internal confidentiality | plaintext segment | encrypted segment | encrypted end-to-end |
| Backend CPU cost | none | none for handshake, none for TLS (LB does both) | full TLS cost |
| L7 features at LB | full | full | none |
| Certificate operations | centralized | centralized plus backend trust anchors | distributed everywhere |
| Compliance fit | trusted internal zones | strict regimes | strictest, zero-trust edges |
| Latency profile | best (one handshake, resumption centralized) | two handshakes per connection pair | one handshake, but at backend |

The governing trade-off: **inspection and efficiency versus internal confidentiality.** Termination buys speed and visibility by trusting the internal network. Pass-through buys absolute confidentiality by giving up both. Re-encryption is the negotiated settlement, paid for in extra handshake CPU and operational complexity.

---

## Common Misconceptions

1. "We use HTTPS, so our traffic is encrypted everywhere." False if you terminate at the edge. The internal segment may be plaintext; say so explicitly in threat models and audits.
2. "TLS is expensive per byte." False on modern hardware. Bulk AES-GCM with AES-NI is cheap; handshakes are the expensive part, which is why resumption, Keep-Alive, and HTTP/2 reuse matter more than cipher micro-optimizations.
3. "Pass-through is strictly more secure." It removes internal eavesdropping but also removes WAF inspection, header hygiene, and centralized certificate control, and it spreads private keys across every backend. Security is redistributed, not increased.
4. "X-Forwarded-For is trustworthy because the LB sets it." Only if the LB overwrites attacker-supplied values and the network guarantees the LB is the sole ingress. Append-mode configs are a spoofing vulnerability.
5. "TLS 1.3 0-RTT is free latency." It introduces replay risk; restrict it to idempotent operations and monitor abuse.
6. "One certificate per domain will not scale on a shared edge." SNI plus ACME automation scales to hundreds of thousands of certificates; wildcards are a convenience, not a requirement, and often a blast-radius liability.

# Topic 8: Global Server Load Balancing (GSLB), GeoDNS, and Anycast

## Intuition First (The Why)
A local load balancer answers one question: which server inside this datacenter should handle this request. But modern platforms run in several datacenters across continents, and a prior question must be answered first: which datacenter should this user reach at all?

Imagine a global bank. A customer in Osaka should not be queued behind a teller window in Frankfurt when a fully staffed branch exists two train stops away. Someone must decide, per customer, which branch serves them, based on distance, branch health, local capacity, and sometimes legal rules about where that customer's records may live. If the Osaka branch floods, the same decision-maker must redirect its customers elsewhere, quickly but without causing a stampede.

Global Server Load Balancing is that decision-maker for the internet. It operates mostly through DNS answers and network routing announcements, steering users to the best region before any local load balancer ever sees a packet.

---

## Detailed Explanation

### What GSLB Is
GSLB is the layer that distributes traffic across geographically separated datacenters or cloud regions. Unlike a local LB, it is usually not in the data path; it influences the data path by controlling which IP address a client resolves (DNS-based GSLB) or by making multiple locations equally addressable so the network itself picks the nearest (anycast-based GSLB).

Its inputs are: the apparent location of the client, measured latency to each region, real-time health of each region, remaining capacity per region, and business policy (data residency, cost, maintenance windows). Its output is a small set of IP addresses, typically the virtual IPs of each chosen region's local load balancer.

### Mechanism 1: GeoDNS (Geographic Routing)
The authoritative DNS server maps the source of the query to a geographic region and answers with that region's VIP.
- Without extensions, the source of the query is the **recursive resolver**, not the client. A user in Mumbai using a resolver in Singapore appears to be in Singapore. This is the classic GeoDNS accuracy failure.
- **EDNS Client Subnet (ECS)** mitigates this: supporting resolvers attach a truncated prefix of the true client IP to the query, so the authoritative server can geolocate the client rather than the resolver. Adoption is broad but not universal, and truncation is a deliberate privacy compromise.
- GeoDNS is cheap, simple, and excellent for coarse steering (continent or country level), which is enough for most cache-heavy consumer traffic.

### Mechanism 2: Latency-Based Routing
Instead of geography, the provider maintains measured round-trip latency tables from networks of vantage points (or from resolver populations) to each region, and answers with the empirically fastest region.
- Geography and latency disagree surprisingly often: cross-border fiber, peering arrangements, and submarine cable topology can make a "farther" region faster.
- This is what managed services like Route 53 latency-based routing or Cloudflare load balancing with dynamic steering implement, continuously re-measuring rather than trusting maps.

### Mechanism 3: Health-Checked Failover and Weighted Policies
- Each region's endpoint is probed from multiple independent vantage points. A region is removed from the answer set only when several geographically separated probes agree it is down, preventing a single broken probe network from evaporating a healthy region.
- Weighted answers enable gradual region canaries (send 5 percent of answers to the new region), maintenance drains (ramp a region's weight to zero), and capacity-based shedding (reduce weight when a region saturates).
- Failover policies define explicit primary/secondary chains for disaster recovery.

### Mechanism 4: Anycast (Network-Layer Global Balancing)
Every point of presence announces the same IP prefix via BGP. Internet routers, following normal BGP path selection, forward each user's packets to the topologically nearest announcing PoP.
- No DNS decision is involved per user; the routing system makes the choice continuously and reconverges in seconds when a PoP withdraws its announcement.
- This is how DNS root servers, CDNs, and large edge networks (Cloudflare, Google) absorb traffic and DDoS at global scale.
- Costs: you must operate BGP and prefix hygiene; policy granularity is coarse (per-prefix, not per-user); and mid-session routing reconvergence can reset in-flight TCP connections, which matters for long-lived sockets.

### How the Pieces Stack
GSLB sits above the funnel from Topic 1: the client resolves a name, GSLB returns a regional VIP, the regional edge LB terminates TLS and routes internally, and internal balancers reach services. GSLB's authoritative servers are themselves deployed as a globally distributed, anycast-addressed fleet, because the phonebook must never be unreachable.

### The TTL Tax: Why Global Failover Is Not Instant
DNS answers are cached by recursive resolvers (and sometimes by OSes, browsers, and misbehaving stubs) for the record's TTL. When GSLB changes an answer set after a region failure, every cache holding the old answer keeps serving it until expiry. User-visible recovery time is therefore: probe detection time plus the remaining TTL of poisoned caches, not the detection time alone. Engineering responses:
- Low TTLs (30 to 60 seconds) for critical names, accepting multiplied authoritative query load and cost.
- Client and edge logic that retries across all returned A records rather than trusting the first.
- Post-landing correction: an edge that detects a mis-steered user (by geo-IP or latency probes from the browser) can issue a redirect to the correct region, paying one extra round trip to escape a stale cache.
- Long-lived connections help: a client already connected to a healthy region is unaffected by DNS staleness.

### Data Residency and Policy Routing
Regulated workloads (GDPR, health data, financial records) require that a user's data be processed in specific jurisdictions. GSLB encodes this as policy: resolve EU users to EU regions regardless of latency. The hard edge case is the traveling user: steering by current location can land them in a region without their data, so production systems combine geo-policy with session or account-affinity hints (for example, a region pin cookie issued at login) so a user keeps reaching their home region for a bounded window.

## Real-World Examples

1. **Amazon Route 53:** exposes geolocation, geoproximity, latency-based, weighted, and failover routing policies with integrated multi-vantage health checks; the canonical managed GSLB.
2. **Cloudflare and Google edge:** anycast prefixes announced from hundreds of PoPs; a PoP or region failure withdraws routes and global traffic reconverges in seconds, which is also why these networks absorb volumetric DDoS close to its source.
3. **Regulated SaaS:** platforms handling EU health or financial data resolve EU-origin queries exclusively to EU regions, overriding latency, and pin logged-in users to their home region via session hints to survive travel and resolver migration.
4. **Region evacuation drills:** mature operators regularly drain an entire region using GSLB weights (ramp weight to zero, verify, restore) so that real disasters execute a rehearsed path instead of an improvised one.

## Internal Working: Mechanics Worth Knowing

1. **EDNS Client Subnet trade-off:** ECS forwards a truncated client prefix (commonly /24 for IPv4) to authoritative servers. It fixes resolver-based geolocation error but leaks partial client location to every authoritative server in the chain; privacy-sensitive resolvers disable it, so GSLB must degrade gracefully to resolver-location mapping.
2. **Answer set composition:** GSLB typically returns multiple IPs per region (the region's redundant local LB VIPs) and shuffles order per response, so client-side retries and round-robin stubs spread load and survive a local LB death without another DNS round trip.
3. **Probe vantage diversity:** health decisions require agreement across independent probe locations and networks; a single-vantage probe plane has itself caused region-scale false failovers when the probe network, not the region, failed.
4. **Anycast and TCP stability:** BGP reconvergence changes the PoP serving an existing flow; stateful connections reset unless the application tolerates reconnects or uses migration-capable transports (QUIC connection migration is the modern answer). Hence anycast shines for short transactions, DNS, and ingestion, while interactive long-lived sessions often prefer DNS-steered, stable endpoints.
5. **Query-load math:** cutting TTL from 300s to 60s multiplies authoritative query volume roughly fivefold for the same client population; GSLB capacity and cost planning must track TTL policy, and browser or OS caches may ignore low TTLs anyway, capping the benefit.
6. **Split-horizon GSLB:** internal resolvers return private regional VIPs to employees and services, while public resolvers receive public VIPs; the same policy engine drives both views.

## Advantages, Disadvantages, and Trade-offs

- **GeoDNS advantages:** simple, inexpensive, sufficient for coarse steering; no client changes.
- **GeoDNS disadvantages:** resolver-based location error without ECS; failover bounded by TTL; no per-flow intelligence.
- **Latency-based advantages:** matches user-perceived speed rather than map distance; adapts to network changes via re-measurement.
- **Latency-based disadvantages:** requires probe infrastructure and continuous measurement; still inherits the TTL tax.
- **Anycast advantages:** second-scale convergence independent of caches; inherent DDoS absorption; zero per-client decision state.
- **Anycast disadvantages:** BGP operational burden; coarse policy granularity; in-flight TCP resets on reconvergence; requires physical PoP expansion to improve reach.
- **The governing trade-off:** failover speed and steering precision versus cache behavior, query cost, and operational complexity. Every multi-region design is a negotiated settlement among these, written down as TTL and policy choices.

---

## Common Misconceptions

1. "GSLB is a box in the data path." False. It is primarily DNS intelligence plus routing announcements; packets rarely traverse a GSLB device.
2. "GeoDNS knows where my user is." It knows where the resolver is, unless ECS is present and honored. Corporate and public resolvers routinely misplace users by continents.
3. "DNS failover is instant because probes detect in seconds." Detection is fast; user recovery is bounded by poisoned caches and TTL, plus client retry behavior.
4. "Anycast and GeoDNS are interchangeable." They operate at different layers with different convergence, policy granularity, and connection-stability properties; many platforms run both (anycast edge, DNS-steered origins).
5. "Setting TTL to 5 seconds solves staleness." Resolver and client misbehavior, query-load explosion, and authoritative capacity make ultra-low TTLs a blunt and partly ineffective instrument.
6. "Global steering replaces local load balancing." GSLB chooses a region entry point; the regional funnel of edge and internal balancers still does the real per-request work.

## AI/ML System Design Perspective

- **Capacity-aware global routing:** GPU scarcity makes capacity a first-class GSLB input. Interactive chat traffic is steered not merely to the nearest region but to the nearest region with free inference capacity and KV-cache headroom, with batch workloads filling the remainder.
- **Residency for prompts:** regulated AI workloads (health, legal, EU public sector) route inference to regions where prompt data may lawfully be processed; model weights are replicated per region precisely so that residency steering never degrades to cross-region inference.
- **Region-level session affinity:** multi-turn conversations benefit from returning to the region holding warm KV cache, so global routers apply soft affinity by session (consistent hashing at region scope), overridable by capacity pressure, mirroring Topic 5's locality-versus-load lesson at planetary scale.
- **Anycast ingestion:** telemetry, logs, and RLHF feedback from devices and agents enter through anycast edges, absorbing bursts close to source before regional processing.

# Topic 9: Client-Side vs Server-Side Load Balancing

## Intuition First (The Why)
Walk into a busy restaurant and two worlds are possible. In one, a host greets you, knows which tables are free, which waiter is overloaded, and which table is reserved, and seats you accordingly. You never see the room; you trust the host. In the other, there is no host: you read the room yourself, notice which tables are empty and which waiters are drowning, and pick your own table. Both systems seat customers; they differ in who holds the map and who makes the choice.

Software has exactly these two worlds. In one, the caller sends its request to a single stable address and an intermediary decides which backend serves it. In the other, the caller itself fetches the list of healthy backends from a registry and chooses per call, handling health, retries, and load locally. The industry calls these server-side and client-side load balancing, and the choice between them determines where your latency hops live, where your blast radius lives, and who must upgrade code when the balancing logic changes.

---

## Detailed Explanation

### What the Two Paradigms Are
The distinguishing axis is not where a proxy process runs; it is **where the per-request decision is made and who owns the topology and health state**.

**Server-side load balancing (intermediary, proxy-based).** The client knows one stable address (a VIP or DNS name). An intermediary (Nginx, HAProxy, a cloud load balancer, an ingress controller) receives each request, consults its own view of backend health gathered by active probes (Topic 4), and forwards the request to a chosen backend using round robin, least connections, weighted pools, or hashing (Topics 2 and 5). The client is dumb by design; all intelligence is centralized.

**Client-side load balancing (smart client, embedded).** The client library contacts a service registry or discovery system (Consul, Eureka, ZooKeeper, Kubernetes Endpoints watched via the API, DNS SRV, or an xDS control plane) to obtain the current endpoint list plus health leases. The library then chooses a backend per call using algorithms such as round robin, least outstanding requests, or power-of-two-choices with latency weighting, and it applies local resilience logic: retries with budgets, outlier ejection, circuit breaking, hedging. Requests go directly to backends; there is no intermediary hop.

**The hybrid: sidecar proxies and service meshes.** A service mesh (Envoy sidecars with an Istio or Linkerd control plane) moves the smart-client logic out of application code into a proxy process that runs beside each caller. The decision point remains local to the caller (one hop on the caller's host, not a centralized fleet), but the logic is language-agnostic and centrally configured by the control plane. Taxonomically this is client-side by decision point and proxy-based by implementation, and it is the modern synthesis the industry converged on to escape the worst flaws of both pure paradigms.

### Why the Paradigm Choice Matters: Nine Dimensions
1. **Hop count and latency.** Server-side adds one network hop per request (sub-millisecond within an availability zone, but it contributes to tail latency and doubles bandwidth transit cost). Client-side connects directly, removing the hop and the intermediary's bandwidth bill.
2. **Coupling and upgrade burden.** A server-side LB is upgraded in one place. A smart client must be upgraded in every service, in every language, by every team; version skew is the classic smart-client operational tax (the reason Netflix-era Ribbon fleets became upgrade nightmares).
3. **Language and protocol coverage.** Server-side is language-agnostic by construction. Client-side requires a correct, maintained library per language, or it silently fragments behavior across the fleet.
4. **Failure modes and blast radius.** A saturated or buggy server-side LB degrades every client simultaneously (centralized failure, centralized fix). A buggy smart-client version degrades only that service's callers (distributed failure, distributed fix). The blast radius inverts between paradigms.
5. **Health-state ownership.** Server-side LBs probe actively and independently. Client-side clients trust registry leases (agents, TTL heartbeats) plus passive signals (outlier ejection on observed errors); a registry partition leaves clients serving from stale lists, gracefully but blindly.
6. **Observability.** Server-side gives one natural choke point for golden signals, rate limits, auth, and audit. Client-side distributes metrics across every caller and requires aggregation infrastructure, but gains per-call context (deadlines, retry counts, queueing observed end-to-end).
7. **Traffic-control granularity.** Central policies (global rate limits, canary weights, mTLS termination, WAF) are trivial server-side. Per-call adaptive signals (client-observed latency including server queueing, deadline-aware shedding) are natural client-side.
8. **Connection versus request balancing.** Long-lived multiplexed protocols (HTTP/2, gRPC) pin many requests to one connection; an L4 server-side LB then cannot balance per request. This single fact reshapes RPC architecture and is detailed below.
9. **Topology fit.** North-south internet traffic is almost always server-side at the edge (TLS, DDoS, WAF). East-west service-to-service traffic is where the paradigm debate lives, and where meshes now dominate mature Kubernetes estates.

### The gRPC Lesson: When Server-Side L4 Silently Fails
gRPC multiplexes many requests over one long-lived HTTP/2 connection. Place a gRPC service behind a naive L4 server-side balancer and each client's single connection pins to one backend; per-request balancing never happens, and one backend can run at 90 percent CPU while its siblings idle. The two standard fixes:
- **Client-side balancing:** the gRPC library resolves names to an endpoint list (via DNS TXT policies, a registry, or xDS) and picks a backend per RPC (pick_first, round_robin, or weighted policies), opening connections as needed.
- **L7 lookaside balancing:** an intermediary that understands HTTP/2 streams (Envoy, a cloud L7 LB, or a gRPC proxy load balancer driven by xDS) balances per stream rather than per connection, restoring server-side semantics at Layer 7.
This lesson generalizes: any protocol whose requests share long-lived connections forces the balancing decision either into the client or up to Layer 7.

### Health and Discovery Mechanics Under Client-Side Balancing
- **Registry leases:** backends register with TTL heartbeats or agent checks; expiry removes them. Clients watch or poll; consistency is eventual, so a client may call a just-dead endpoint once, which is why retries with budgets and idempotency discipline are mandatory companions.
- **Passive health (outlier ejection):** clients eject endpoints that exhibit high error rates or latency over a sliding window, with parameters for ejection interval, base ejection time, and maximum ejection percentage (to avoid ejecting an entire fleet during a global slowdown).
- **Active checks optional:** sophisticated clients also run low-frequency active probes to rediscover recovered endpoints faster than traffic alone would.
- **Thundering herd discipline:** on registry restart, staggered reconnects with jitter prevent every client from slamming the control plane simultaneously.

### Load Algorithms by Paradigm
- **Server-side:** round robin, weighted round robin, least connections, consistent hashing (Topic 10), IP hash (Topic 5). The LB sees aggregate connection state, so global least-connections is genuinely global.
- **Client-side:** round robin, weighted, least outstanding requests, power-of-two-choices (P2C) with exponentially weighted moving average latency (the Finagle and modern gRPC default), outlier ejection, deadline-aware shedding, and hedged requests for idempotent calls (with strict retry budgets, commonly around 10 percent plus a small token reserve, to avoid retry storms).
- **The honest comparison:** P2C with local latency feedback is excellent and needs no shared state, but it optimizes the client's own view; a central LB sees the aggregate. Neither is universally better; they see different signals.

### Decision Guide: Which Paradigm When
- **North-south internet ingress:** server-side edge LB, always (TLS termination, DDoS, WAF, audit choke point).
- **East-west in a mature Kubernetes estate:** service mesh sidecars (client-side decision point, central policy ownership).
- **Polyglot org without mesh maturity:** internal server-side LBs per service for simplicity, with mesh adoption as the migration target; accept the extra hop as the price of language agnosticism.
- **High-performance RPC fabrics (gRPC, Thrift):** client-side policies or L7 lookaside; never naive L4.
- **Batch and data jobs against stateless fleets:** simple client-side round robin from a registry; the hop removal matters at millions of calls.
- **Regulated workloads requiring central audit and rate-limit choke points:** server-side, even east-west.

---

## Mental Model and Analogy
- **Server-side:** the restaurant host. One trusted decision-maker with the global view; you never see the room; when the host is overwhelmed, everyone waits together.
- **Client-side:** reading the room yourself. No hop, no host to fail, but every diner must learn the same seating skill, and a diner with outdated instincts picks a dead table.
- **Service mesh:** a personal assistant who walks in with you, reads the room using centrally issued rules, and picks your table in your own language. The decision stays local; the ownership stays central.

## Real-World Examples

1. **The Netflix era and its retirement:** Ribbon plus Eureka defined client-side balancing for a generation, then collapsed under per-language upgrade fatigue and version skew; the industry's migration to Envoy-based meshes is the direct lesson that smart-client logic belongs outside application code.
2. **gRPC load-balancing policies:** pick_first, round_robin, and weighted targets in the client, plus xDS-driven lookaside balancers for stream-level server-side control; the canonical case study of connection pinning forcing the decision client-side or up to Layer 7.
3. **Kubernetes east-west:** kube-proxy IPVS or iptables DNAT (a distributed, node-local form of server-side balancing), headless Services with client-side endpoint selection, and Istio or Linkerd meshes; one cluster routinely runs all three paradigms simultaneously.
4. **Finagle and Linkerd:** P2C with EWMA latency and outlier ejection as the reference client-side algorithm suite, later embedded in mesh data planes.
5. **Cloud internal LBs:** teams without mesh maturity run internal NLB or ALB per service for east-west traffic, accepting the hop as the price of zero client-library ownership.

## Internal Working: Mechanics Worth Knowing

1. **Registry consistency window:** with TTL leases of 10 seconds and client caches of 30, a backend death produces a bounded window of dead-endpoint calls; retry budgets, idempotency keys, and outlier ejection convert that window from an outage into a sub-percent error blip.
2. **Outlier ejection parameters:** ejection interval, base ejection time, maximum ejection percentage, and success-rate thresholds; misconfigured maxima have ejected entire fleets during global latency events, turning degradation into self-inflicted outage.
3. **Retry and hedging discipline:** retry budgets (commonly 10 percent plus a small token reserve), hedging only for idempotent or cancel-safe calls, and deadline propagation to prevent retry storms from amplifying the very overload they attempt to escape.
4. **Connection versus request balancing:** HTTP/2 and gRPC stream pinning makes L4 server-side balancing blind per request; the fixes are client-side per-call selection or L7 stream-aware lookaside, and this single mechanic decides RPC fabric architecture.
5. **mTLS and identity ownership:** smart clients must each hold, rotate, and present certificates; meshes centralize certificate issuance and rotation in the control plane while keeping termination local, which is a large part of the mesh value proposition.
6. **Observability aggregation:** client-side metrics live in every caller process; service-level golden signals require a metrics pipeline with per-service aggregation, whereas a server-side LB emits them natively at one choke point.

---

## Advantages, Disadvantages, and Trade-offs

- **Server-side advantages:** language-agnostic; one upgrade point; central policy, audit, and rate-limit choke point; aggregate health view; simple clients.
- **Server-side disadvantages:** extra hop and doubled bandwidth transit; centralized blast radius and bottleneck; L4 blindness to multiplexed protocols; LB fleet cost and operations.
- **Client-side advantages:** no intermediary hop; per-call adaptive signals (client-observed latency, deadlines); distributed blast radius; no LB fleet bandwidth cost.
- **Client-side disadvantages:** per-language library maintenance and version skew; registry infrastructure and its failure modes; stale-view windows; distributed observability burden; upgrade fatigue across teams.
- **Mesh trade-offs:** keeps decisions local and ownership central, language-agnostic without a hop to a central fleet; costs control-plane operations, sidecar resource overhead, and organizational maturity.
- **The governing trade-off:** centralization of ownership versus locality of decision. Every architecture in this space is a point on that line, and the mesh exists precisely to decouple the two axes that pure paradigms fuse together.

---

## Common Misconceptions

1. "Client-side balancing means no infrastructure." The infrastructure moves, it does not vanish: you now own a registry, per-language libraries, and aggregated observability.
2. "Server-side always costs an extra hop of latency." Node-local DNAT, DSR, and anycast variants blur the hop, and within one availability zone the hop is sub-millisecond; tail behavior and bandwidth cost matter more than the mean.
3. "A service mesh is server-side balancing because it uses proxies." Taxonomy follows the decision point, not the process boundary: mesh decisions are made at the caller's host, which is client-side locality with proxy implementation.
4. "Client-side balances better because it sees everything." It sees its own view; a central LB sees the aggregate. P2C with local feedback is excellent but global least-connections requires shared state neither paradigm has for free.
5. "gRPC works fine behind an L4 load balancer." Connection pinning makes per-request balancing impossible; streams stick to one backend until the connection dies.
6. "Smart clients are obsolete now that meshes exist." Meshes demand operational maturity; many organizations run smart clients or plain DNS plus retries successfully at small scale, and gRPC client policies remain standard inside RPC fabrics.

- **Resilience discipline:** retry budgets, ejection maxima, idempotency, deadline propagation; resilience mechanisms themselves cause the classic outages.

# Topic 10: What is Consistent Hashing? (Hash Rings, Virtual Nodes, Rendezvous Hashing)

## Intuition First (The Why)
You run a cache fleet of four servers and you assign keys with the obvious formula: server = hash(key) mod 4. It works beautifully, until Black Friday, when you add a fifth server to absorb load. The moment N changes from 4 to 5, the formula changes for almost every key: roughly 80 percent of your keys now map to a different server than yesterday. Every cache miss slams the database at once, latency spikes for fifteen minutes, and the "scaling event" becomes an outage. This is the mod-N catastrophe.

What you actually want is a mapping with a modest promise: when a node joins or leaves, only the keys that logically belong to the new or departed node should move, roughly one Nth of the keyspace, and everything else stays exactly where it was. Consistent hashing is the family of techniques that keeps that promise. It is the quiet machinery behind cache fleets, sharded databases, replica placement, load-balancer connection tracking, and session affinity.

---

## Detailed Explanation

### The Problem With mod-N, Quantified
With server = hash(key) mod N, a key stays on the same server after N changes only when hash mod N_old equals hash mod N_new. For N going from 4 to 5, that coincidence holds for only about 20 percent of keys (the residues where k mod 4 equals k mod 5), so about 80 percent of keys remap. In general, adding one node to N remaps approximately (N_new minus 1) over N_new of the keyspace. The churn is proportional to everything, not to the change.

### Mechanism 1: The Hash Ring
Consistent hashing places both keys and nodes on the same circular hash space, typically the output range of a 32-bit or 64-bit hash function wrapped into a ring from 0 to 2^m minus 1.
- Hash each node's identifier (for example, its IP plus port, or a node UUID) onto the ring.
- Hash each key onto the same ring.
- A key's owner is the first node encountered walking clockwise from the key's position (the successor rule).
- **Add a node:** it lands somewhere on the ring and takes ownership only of keys in the arc between itself and its clockwise predecessor. All other keys keep their owners. Movement is bounded by roughly K over N keys.
- **Remove a node:** its keys move to its clockwise successor; nothing else moves.
Contrast with mod-N: adding a fifth node to four moves about 20 percent of keys on a ring (the new node's share) instead of about 80 percent.

### The Raw Ring's Flaw: Uneven Arcs
Random points on a circle do not space themselves evenly; arc lengths follow an exponential distribution. With four nodes, one node can easily own half the ring and become a hotspot while another owns a sliver. The raw ring solves churn but not balance.

### Mechanism 2: Virtual Nodes (vnodes)
Give each physical node many points on the ring (commonly 100 to 256, for example ketama's roughly 160 points per server or Cassandra's 256 tokens) instead of one.
- Each physical node's load becomes the sum of many small arcs, and by the law of large numbers the sums equalize: balance is restored.
- Hotspot absorption improves: a hot key range is split across many owners' arcs rather than landing on one node.
- Rebalance parallelism improves: when a node leaves, its keys scatter to many different successors (all the nodes owning neighboring arcs), so recovery load spreads across the fleet instead of hammering one successor.
- Weights become expressible: a node with double capacity gets double the vnode count.

### Mechanism 3: Rendezvous Hashing (Highest Random Weight)
A ring-free alternative from Thaler and Ravishankar (1996).
- For a key, compute a score for every node: score(node) = H(node identifier concatenated with key), a deterministic pseudo-random number.
- The key's owner is the node with the highest score. Think of it as a sealed-bid auction where every node bids a number derived from (node, key), and the highest bid wins.
- **Add a node:** only keys whose previous winner was lower than the new node's bid change owner; all other keys keep the same maximum and never notice.
- **Remove a node:** only the keys it won are re-auctioned.
- Balance emerges naturally without vnodes, because scores are uniform random per (node, key) pair.
- Weighted variant: transform scores, for example score = hash raised to (1 over weight), or score = minus weight over ln(hash normalized), so stronger nodes win proportionally more keys.
- Cost: O(N) hash computations per lookup (reducible to O(log N) with tree or skeleton structures), which is perfectly fine for fleets of a few dozen nodes and prohibitive for thousands.

### Mechanism 4: Industry Variants Worth Knowing
- **Pre-split slots (Redis Cluster):** fix the hash space into a constant number of slots (Redis uses 16384, via CRC16(key) mod 16384). Keys map to slots forever; slots map to nodes via a small ownership table. Scaling moves whole slots (bulk data migration) and never recomputes key-to-space mapping. Client logic is trivial; the price is fixed granularity (the slot count caps shard parallelism).
- **Maglev hashing (Google):** each node gets a permutation of a lookup table of prime size M; the table is filled by interleaving permutations, yielding O(1) lookups, near-perfect balance, and bounded disruption on membership change. Used in Google's Maglev load balancers for connection tracking and exposed in Envoy as the Maglev LB policy.
- **Consistent hashing with bounded loads (Google research):** augment the ring with a capacity cap c = (1 + epsilon) times mean load. If a key's successor is already above c, walk clockwise to the next node. This guarantees balance within (1 + epsilon) while keeping movement near O(K over N), closing the last gap between consistency and load awareness.
- **Hierarchical placement (Ceph CRUSH):** a weighted, topology-aware cousin that places replicas across racks and rooms by computing placement from the map itself, without per-key metadata.

### Replication on the Ring
Sharded stores place replicas by walking clockwise from the key and taking the next R distinct physical nodes (the preference list in Dynamo and Cassandra). Rack or datacenter awareness filters candidates so replicas land in distinct failure domains. Read and write quorums then operate over that preference list, connecting this topic directly to Topic 18 (Replication) and Topic 21 (CAP) of Chapter 1.

### Hash Function Discipline
The hash must be fast, uniform, and, above all, stable. MurmurHash, xxHash, or CRC-based hashes are typical; cryptographic hashes are unnecessary. Changing the function, its seed, or its output width in production remaps the entire keyspace, which is exactly the mod-N catastrophe self-inflicted. Pin the function in configuration and treat it as a wire-format contract.

## Mental Model and Analogy
- **The ring:** a round banquet table. Guests (keys) are seated with the first host (node) clockwise from their place. When a new host joins the table, only the guests seated between the new host and the previous host change hosts; everyone else keeps eating undisturbed.
- **Rendezvous:** a sealed-bid auction per key. Every node submits a deterministic bid computed from its identity and the key. The highest bid wins. If a bidder leaves the market, only the lots it won are re-auctioned; every other lot's winner is unchanged.
- **vnodes:** each host places many name cards around the table instead of one, so no host accidentally owns a huge contiguous stretch of guests.

## Real-World Examples

1. **Amazon Dynamo (2007):** the canonical production deployment. Consistent hashing with virtual nodes partitions the keyspace; replicas are the next distinct nodes clockwise; adding or removing storage nodes moves only neighboring arcs, which is how Dynamo scales without reshuffling the world.
2. **Apache Cassandra:** tokens per node, later 256 virtual nodes by default, with rack-aware replica placement walking the ring; rebalancing streams only the affected ranges.
3. **Memcached clients (ketama):** the classic cache-fleet ring with roughly 160 points per server, chosen precisely so that adding a cache server causes a small, bounded miss storm instead of a total flush.
4. **Redis Cluster:** the pre-split-slot variant: 16384 slots via CRC16 mod 16384, slot ownership tables, and slot migration for rebalancing; operationally simpler than ring walking at the cost of fixed granularity.
5. **Google Maglev and Envoy:** Maglev's permutation table gives O(1) consistent placement for load-balancer connection tracking; Envoy exposes ring_hash and Maglev policies so session affinity (Topic 5) survives fleet changes with minimal remapping.
6. **CDN and cache fleets:** object keys are consistently hashed so a given object always lands on the same cache server, keeping hit rates high while caches join and leave the fleet daily.

## Internal Working: Mechanics Worth Knowing

1. **Ring lookup cost:** a sorted array of vnode hashes plus binary search gives O(log V) per key, V being total vnode count; Maglev's filled table gives O(1); rendezvous gives O(N) unless tree-optimized.
2. **Vnode count tuning:** too few vnodes leave uneven arcs and hotspots; too many inflate metadata and slow membership changes. Production fleets commonly sit between 100 and 256 per node, tuned by measured load variance.
3. **Weighted placement:** vnode counts proportional to capacity on rings; score transforms (hash to the power 1 over weight, or negative weight over log of normalized hash) in rendezvous; permutation scheduling weights in Maglev.
4. **Bounded loads:** with cap c = (1 + epsilon) times mean load, an overloaded successor is skipped clockwise; this converts consistent hashing from "consistent but possibly hot" into "consistent and provably balanced", at the cost of slightly more movement under skew.
5. **Replica walks and failure domains:** the preference list skips nodes in the same rack or datacenter as an already-chosen replica, binding consistent hashing into the failure-domain model of the cluster.
6. **Rebalance throttling:** moving a node's arcs streams real data; production systems throttle migration bandwidth and prioritize foreground traffic, because an unthrottled rebalance has taken down more clusters than any hash collision ever did.

---

## Advantages, Disadvantages, and Trade-offs

- **mod-N:** O(1) and trivial, but churn proportional to the whole keyspace on any membership change; unacceptable beyond toy fleets.
- **Ring plus vnodes:** churn bounded near K over N, good balance, weighted support, O(log V) lookup; costs vnode metadata and tuning.
- **Rendezvous:** no ring metadata, natural balance, elegant weighting, minimal churn; costs O(N) hashing per lookup, limiting fleet size.
- **Maglev and table methods:** O(1) lookup, excellent balance, bounded disruption; costs table memory and rebuild work on membership change.
- **Pre-split slots:** trivial client math and bulk migration; costs fixed granularity and an ownership table to distribute.
- **The governing trade-off:** lookup cost versus disruption bound versus balance quality versus metadata complexity. Every variant is a different point on that four-axis surface, and the right choice follows fleet size, lookup frequency, and operational appetite.

---

## Common Misconceptions

1. "Consistent hashing balances load perfectly by itself." The raw ring does not; arc lengths are exponentially distributed. Balance comes from vnodes, bounded loads, or table methods.
2. "Adding a node moves zero keys." It moves about K over N keys, the new node's fair share. Bounded churn, not zero churn, is the guarantee.
3. "Rendezvous hashing is an obsolete curiosity." It is simpler than rings, weights elegantly, and powers real systems at modest fleet sizes; O(N) is not a problem when N is a dozen.
4. "Consistent hashing is only for caches." It partitions sharded databases, places replicas, tracks LB connections, pins sessions, and routes vector shards; it is a general placement primitive.
5. "Any hash function will do." Poor uniformity creates hot arcs, and changing the function or seed in production remaps everything; hash stability is a production contract.
6. "Redis Cluster uses consistent hashing." It uses fixed hash slots, a pre-split relative of consistent hashing with different operational properties.

# Topic 11: What is Sharding? (Shard-Aware Routing, Rebalancing, and Hotspots)

## Intuition First (The Why)
Chapter 1 established what sharding is: splitting one dataset into disjoint pieces stored on different machines so writes and storage scale beyond a single node. This topic tackles the three problems that make sharding hard in production, the three places where sharded systems actually break.

Imagine a city library system with many branch libraries. Three operational questions decide whether the system works. First, **routing**: when a reader asks for a book, how does the system instantly know which branch holds it, without asking every branch? Second, **rebalancing**: when a new branch opens or a neighborhood grows, how do you relocate thousands of books while the libraries stay open and readers keep borrowing? Third, **hotspots**: when one book goes viral and every reader in the city queues at the single branch holding it, what do you do about the branch that is drowning while the others idle?

Shard-aware routing, rebalancing, and hotspot management are exactly these three questions. Master them and sharding becomes an engineering discipline; ignore them and sharding becomes an outage generator.

---

## Detailed Explanation

### Part 1: Shard-Aware Routing

Every sharded system must answer: given a key, which shard owns it, and how does the request get there with minimum hops and maximum freshness of topology knowledge? Three routing models exist.

**Model A: Smart Client (client-aware routing).**
The client library holds the shard map (token ranges, slot ownership, key-space partitions) fetched from a control plane or gossip protocol, computes the shard locally, and connects directly to the owning node.
- Advantages: no intermediary hop, no central router bottleneck, per-call adaptive logic possible.
- Disadvantages: every client language must implement and update the map; topology changes propagate asynchronously, so clients briefly route to old owners and must handle redirects or retries; upgrade burden across teams.
- Examples: Cassandra drivers holding the token ring, Redis Cluster clients holding the 16384-slot map.

**Model B: Proxy Router (central routing layer).**
A router tier holds the authoritative shard map and forwards each request to the owning shard. Clients speak to one endpoint and remain shard-ignorant.
- Advantages: language-agnostic clients, one place to upgrade routing logic, natural choke point for cross-shard merges, auth, and metrics.
- Disadvantages: one extra network hop, router fleet becomes a scaling and availability concern (it must itself be redundant and horizontally scaled), central blast radius.
- Examples: mongos for MongoDB sharded clusters, Vitess VTGate, shard-aware API gateways.

**Model C: Server-Side Forwarding (any-node entry).**
Any shard can accept any request; if it does not own the key, it forwards internally to the owner and relays the response.
- Advantages: zero client topology knowledge, simple clients, graceful during topology churn.
- Disadvantages: misrouted requests cost an intra-cluster hop and double the work on the receiving path; internal forwarding can cascade under skew.
- Examples: Cassandra accepting writes on any node and routing to replicas, some distributed key-value stores.

Production systems often blend: smart clients for hot paths, proxies for polyglot edges, forwarding as a safety net.

**Redirect protocols as topology signals.**
Redis Cluster formalizes topology churn in two client-visible redirects. MOVED means ownership permanently changed: update your slot map and retry at the new node. ASK means a slot is mid-migration: the key may live on the target node temporarily, so ask there once without rewriting your map. Clients that treat these as errors instead of normal control signals break during every rebalance; clients that handle them make rebalancing invisible.

**Queries without the shard key: scatter-gather and index shards.**
A query that does not contain the shard key (for example, look up orders by email when shards are keyed by user_id) must fan out to every shard, collect partial results, and merge: scatter-gather. Its cost model is unforgiving: latency equals the slowest shard's response, and total work equals the sum across shards, so it degrades as the fleet grows.
Three standard mitigations:
1. **Index shards (secondary sharded indexes):** maintain a second logical table sharded by the secondary key (email to user_id mapping), turning scatter-gather into a two-hop directed lookup. DynamoDB global secondary indexes and Cassandra secondary indexes automate variants of this.
2. **Copy tables (denormalized reverse mappings):** application-maintained reverse-lookup tables, paid for with write amplification.
3. **Accept scatter-gather for rare paths:** admin tools and analytics can fan out; user-facing hot paths must not.

**Cross-shard operations: the tax ledger.**
- **Transactions:** cross-shard ACID requires two-phase commit or consensus across owners, which is slow and failure-prone; production systems confine transactions to a shard and compose cross-shard business flows as sagas with compensation actions.
- **Joins:** co-locate related rows under the same shard key (for example, embed customer_id into order keys) so joins stay intra-shard; otherwise join via scatter-gather or application-side merging.
- **Global uniqueness:** enforce uniqueness either by routing on the unique attribute itself or by issuing identifiers from a coordinator that embeds shard identity (Snowflake-style IDs), never by scanning all shards.
- **Pagination and aggregation:** per-shard cursors merged by the router (k-way merge on sort key), and partial aggregates computed per shard then combined; both are correct but cost proportional to shard count, which is why shard counts are kept as small as capacity allows.

### Part 2: Rebalancing

Rebalancing moves shard ownership and data as the fleet grows, shrinks, or skews. It is the most dangerous routine operation in a sharded system because it migrates live data under live traffic.

**Movement strategies by placement scheme.**
1. **Range systems (Bigtable, HBase, MongoDB):** data lives in sorted ranges or chunks. Rebalancing splits oversized or overhot ranges in place, then migrates halves to new owners. Boundaries move; the key space is continuous.
2. **Hash systems with rings or slots (Cassandra, Redis Cluster, DynamoDB internals):** ownership is a set of ranges on a hash ring or a list of pre-split slots. Rebalancing migrates whole ranges or slots between nodes; consistent hashing (Topic 10) bounds the movement to the affected arcs.
3. **Directory systems:** a lookup service owns an explicit key-to-shard map; rebalancing rewrites map entries and migrates the referenced data. Maximum flexibility, maximum metadata burden.

**Pre-splitting: rebalancing without rehashing.**
Mature systems fix the hash space into a large constant number of logical shards on day one (Redis Cluster's 16384 slots, MongoDB's initial chunk splits, DynamoDB's internal partitions). Keys map to logical shards forever; logical shards map to physical nodes via a small ownership table. Rebalancing then moves whole logical shards as units: no key ever changes its logical home, clients keep trivial math, and migration is bulk copy plus cutover. The split count is a capacity forecast: enough logical shards to keep the largest node's share small for years, not so many that metadata and scatter-gather merge costs dominate.

**The safe migration sequence (fenced cutover).**
A range or slot move must never allow two owners to accept writes simultaneously. The production sequence:
1. **Assign:** the balancer records the new owner with a monotonic epoch or generation number; the old owner is fenced for that range at the new epoch, meaning its writes for the range carry a stale epoch and are rejectable.
2. **Snapshot:** the new owner copies the range's current data from the old owner while the old owner continues serving writes and logging them.
3. **Catch-up:** the new owner replays the log tail until lag approaches zero.
4. **Cutover:** reads and writes switch to the new owner; storage rejects any write bearing an epoch older than the current one, making split-brain writes impossible even if a stale router misroutes.
5. **Cleanup:** the old owner deletes its copy after a verification window (checksums, row counts, sampled reads).
Skipping or reordering these steps produces the classic rebalancing corruption stories: lost updates during copy, duplicate divergent writes during cutover, or reads served from a half-copied range.

**Throttling, scheduling, and hysteresis.**
Migration consumes network, disk, and CPU that foreground traffic also wants. Production balancers cap migration bandwidth, pause during peak windows or incident freeze periods, and apply hysteresis thresholds (move only when imbalance exceeds, say, 15 percent, and stop before perfect equality) so the balancer does not flap shards back and forth on diurnal load waves. Unthrottled rebalances have caused more sharded-cluster outages than any hash collision.

**Observability for rebalancing.**
Track migration lag per moving range, epochs in flight, redirect rates (MOVED/ASK spikes signal churn), per-shard size and heat distributions, and verification results. A rebalance without dashboards is a gamble with the dataset.

### Part 3: Hotspots

A hotspot is a shard receiving load disproportionate to its share, while siblings idle. It is the most common real-world failure of sharded systems, and it is almost always a key-design or access-pattern problem, not a capacity problem.

**Root causes.**
1. **Monotonic shard keys:** sharding by timestamp or auto-increment ID sends every new write to the leading edge of the key space, melting one shard while the rest sleep. The classic time-series mistake.
2. **Low-cardinality keys:** sharding by status, country, or type concentrates all traffic of the largest category on one shard.
3. **Whale tenants and celebrities:** one tenant or user with enormous fan-out (a viral account, an enterprise customer with millions of records) owns one shard's worth of heat by construction.
4. **Bulk jobs:** a batch export scanning one ID range, or a nightly job keyed by date, pins a single shard.
5. **Hot single keys:** one globally popular object (a trending post, a flash-sale product) concentrates reads on its owner shard regardless of fleet size.

**Detection.**
Monitor per-shard CPU, queue depth, p99 latency, and request rate, and alert on skew ratio (maximum shard over median shard) rather than on fleet averages, because averages hide hotspots by design. Heat tables and per-shard dashboards make the drowning branch visible before users do.

**Mitigations, with their prices.**
1. **Hash or salt the key:** replace timestamp with hash(entity_id) or with (time_bucket, random_suffix). Writes spread evenly; the price is that native time-range scans become scatter-gather or require an index shard.
2. **Bucketed keys with read-side merge:** write hot entities under K salted sub-keys (user_id#0 through user_id#K-1) and merge K partial results on read. Writes spread by K; reads pay K times. Tune K to the skew.
3. **Fan-out inversion for social graphs:** shard timelines by follower instead of followee so a celebrity's post triggers writes to many followers' shards rather than reads from one hot shard. The price inverts: write amplification per post. Hybrids cache celebrity timelines and fan out only for normal accounts, which is exactly what large social platforms run.
4. **Cache and rate-limit in front of the hot shard:** for read hotspots, a cache layer (Chapter 1, Topic 15) absorbs the storm; per-key rate limiting sheds abusive load. The price is staleness windows and shed requests.
5. **Isolate whales:** dedicate a shard or pool to extreme tenants (noisy-neighbor isolation), protecting the shared fleet's tail latency. The price is capacity fragmentation and operational tiers.
6. **Replica reads and bounded loads:** serve hot read traffic from replicas of the hot shard, and use bounded-load placement (Topic 10) so affinity never overrides saturation.
7. **Split on heat:** range systems split hot ranges in place (HBase region splits, MongoDB chunk splits, DynamoDB partition splits on heat). Note the limit: if every key in a range shares the hot prefix, the range cannot split usefully; MongoDB calls these jumbo chunks, and they are the system telling you your shard key is wrong.

**The governing insight:** adding shards does not fix a hotspot, because the hot key still hashes or ranges to exactly one shard. Hotspots are fixed by changing key distribution, inverting fan-out, caching, or isolating; never by naive horizontal addition.

## Mental Model and Analogy
- **Routing:** the library catalog. A smart client carries a personal copy of the catalog (updated asynchronously, occasionally stale); a proxy router is the central desk that always has the current catalog; server-side forwarding is asking any librarian who then walks it to the right branch themselves.
- **Rebalancing:** relocating books between branches while both stay open: label the moving collection with a new edition number (epoch), copy the shelves, catch up on loans made during the copy, flip the catalog entry, then clear the old shelves.
- **Hotspot:** the branch holding the viral bestseller. Opening more branches does nothing until you print more copies (replicas), split the queue into K desks (salted sub-keys), or move the signing event to a stadium (isolation).

## Real-World Examples

1. **DynamoDB partitions:** AWS splits partitions on size and heat, and adaptive capacity redistributes throughput to hot partitions temporarily; customers still see hot-partition throttling when key design concentrates load, which is why AWS documentation spends pages on shard-key design.
2. **MongoDB chunks and jumbo chunks:** the balancer migrates chunks between shards; a chunk that cannot split because all documents share the shard-key prefix becomes a jumbo chunk, the canonical symptom of a monotonic or low-cardinality shard key.
3. **Vitess resharding:** the workflow copies a keyspace range to new shards, streams live changes via vreplication until lag is zero, then cuts over writes and reads in a controlled window, exactly the fenced sequence described above, with rollback until the point of no return.
4. **Twitter-style timeline fan-out:** fan-out on write to follower shards for normal users, cached materialized timelines for celebrities, a hybrid that balances the write amplification against read hotspots at planetary scale.
5. **Redis Cluster migrations:** slots move with ASK redirects during the window and MOVED after, letting compliant clients ride rebalances without errors.

## Internal Working: Mechanics Worth Knowing

1. **Topology versions and map freshness:** clients and routers cache shard maps tagged with a version; topology changes bump the version and propagate via push (control plane) or pull (gossip); redirect protocols cover the stale window so correctness never depends on perfect freshness.
2. **Epochs as fencing tokens:** storage layers reject writes whose epoch is older than the range's current epoch, converting a distributed coordination problem into a simple monotonic comparison at the storage layer.
3. **Verification after migration:** checksums over migrated ranges, row-count reconciliation, and sampled read comparisons run before cleanup; silent partial copies are the rebalancing failure mode that surfaces weeks later as missing data.
4. **Scatter-gather merge costs:** k-way merge for sorted pagination keeps per-shard cursors; partial aggregation pushes computation to shards; both scale with shard count, which is a quiet argument for keeping shard counts minimal for current capacity plus one growth step.
5. **Shard-key entropy versus locality:** hash keys maximize spread and destroy range locality; range keys maximize locality and risk monotonic heat. Composite keys (tenant prefix plus hash suffix, or bucket plus entity) are the engineered compromise, chosen per access pattern.
6. **Co-location as a design primitive:** embedding the parent's shard key into child keys (user_id prefix on orders, sessions, and carts) keeps entity graphs intra-shard, converting future cross-shard transactions into single-shard transactions; this single decision prevents most cross-shard pain at schema time.

## Advantages, Disadvantages, and Trade-offs

- **Sharding advantages:** write throughput and storage scale near-linearly with shard count; fault isolation between shards; tenant isolation possible by construction.
- **Sharding disadvantages:** cross-shard queries, transactions, uniqueness, and pagination all pay taxes; rebalancing is a live-data surgery; hotspots concentrate load regardless of fleet size; operational surface multiplies (per-shard monitoring, backups, restores).
- **Routing model trade-off:** hop count and client simplicity versus map freshness and central blast radius.
- **Rebalancing trade-off:** movement granularity (slots versus ranges versus directory entries) versus metadata cost and migration complexity.
- **Hotspot trade-off:** spread (hashing, salting) versus locality (range scans, cache affinity); every mitigation buys balance with either read amplification, write amplification, or staleness.
- **The governing trade-off:** sharding converts a capacity problem into a distribution problem. Capacity is bought with money; distribution is bought with design discipline, and the design decisions (shard key, co-location, pre-split count) are made early and resist change.

---

## Common Misconceptions

1. "Sharding fixes read scale." Reads scale through replication and caching; sharding addresses writes and storage. A hot read key still melts one shard plus its replicas.
2. "Rebalancing is automatic and free." It competes with foreground traffic for network and disk, requires throttling and windows, and can flap without hysteresis; automatic does not mean harmless.
3. "A hotspot means we need more shards." The hot key maps to one shard before and after adding shards; only key redistribution, fan-out inversion, caching, or isolation changes the heat map.
4. "MOVED and ASK redirects are errors." They are healthy topology-change signals; robust clients treat them as control messages, and rebalances become invisible.
5. "Cross-shard joins are impossible, so denormalize everything." Selective denormalization plus index shards for hot secondary patterns plus tolerated scatter-gather for rare paths is the balanced professional answer.
6. "Pre-splitting prevents hotspots." Pre-splitting bounds rebalance movement and fixes granularity; hotspots originate in key design and access skew, which pre-splitting cannot touch.

## AI/ML System Design Perspective

- **Vector index sharding:** billion-embedding indexes split into shards placed by consistent hashing or slots; similarity queries scatter to shards, over-fetch local nearest neighbors, and merge globally, trading over-fetch factor for recall under shard count. Rebalancing moves whole shards; hot entity ranges (viral items) are mitigated by replica fan-out for query traffic.
- **Feature stores and entity hotspots:** feature rows shard by entity ID; viral entities (trending products, popular creators) are salted into sub-keys with read-side merge, exactly the classic pattern, because feature serving latency budgets cannot absorb a hot shard.
- **Training data placement:** dataset shards pre-split into slots assigned to elastic worker pools; preemptible GPU churn triggers slot migration, and checkpoint boundaries double as safe cutover points, making epochs natural fencing boundaries.
- **Serving tenancy:** a single viral application tenant can saturate one GPU pool; whale isolation (dedicated pools) plus bounded-load routing keeps shared inference fleets' tail latency intact, mirroring noisy-neighbor isolation in sharded storage.

## Revision Sheet

- **Routing models:** smart client (direct, stale-map redirects), proxy router (hop, central map), server-side forwarding (any-node entry, intra hop).
- **Redirects:** MOVED = permanent ownership change; ASK = temporary migration probe.
- **No shard key in query:** scatter-gather (latency = slowest shard, work = sum), index shards, copy tables, or tolerate for rare paths.
- **Cross-shard taxes:** 2PC or sagas for transactions, co-location for joins, coordinator IDs for uniqueness, k-way merge for pagination.
- **Rebalancing strategies:** range split-and-move, ring/slot migration, directory remap; pre-split logical shards make moves bulk and clients trivial.
- **Safe migration:** assign with epoch, fence old owner, snapshot, replay tail, cut over, verify, cleanup; storage rejects stale epochs.
- **Balancer discipline:** throttle, window, hysteresis, dashboards on skew ratio.
- **Hotspot causes:** monotonic keys, low cardinality, whales, bulk jobs, hot single keys.
- **Hotspot fixes:** hash or salt keys, bucketed sub-keys with read merge, fan-out inversion, cache and rate-limit, whale isolation, replica reads, split on heat; adding shards alone fixes nothing.
- **Design rule:** co-locate child keys under parent shard keys at schema time; the shard key is a contract about future access patterns.

# Topic 12: Industry Tools: Nginx, HAProxy, Envoy, Cloud LBs, Kubernetes

## Intuition First (The Why)
Every concept in this chapter, algorithms, health checks, termination, redundancy, hashing, is a primitive. Primitives do not ship themselves; they ship inside tools. And the tools differ less in what they can do than in three decisive questions: where the configuration lives (a file, an API, or a managed control plane), how the tool learns topology (static lists, DNS, registries, or pushed endpoint streams), and how it applies change (reload, seamless handoff, or live push).

Choosing a load-balancing tool is therefore not a feature checklist exercise; it is a decision about your operational model. A team that wants a file in Git and a reload picks a different tool than a team that wants per-call telemetry and control-plane-driven fleets, and both are right for their context. This topic maps the five tool families the industry actually runs: Nginx, HAProxy, Envoy, managed cloud load balancers, and the Kubernetes networking stack, then gives you the selection logic that ties them together.

---

## Detailed Explanation

### Family 1: Nginx
Born as a web server, matured into the world's most deployed reverse proxy and load balancer.
- **Architecture:** event-driven, asynchronous, non-blocking. A small number of worker processes (typically one per core) multiplex tens of thousands of connections using epoll or kqueue, which is why one modest box fronts enormous traffic (Chapter 1, Topic 23 is the reason this works).
- **Layers:** L7 via the http block; L4 via the stream module.
- **Algorithms:** round robin with smooth weighted interleaving, least_conn, ip_hash, random, and generic hash (keyed on URI, header, or cookie, giving consistent-hash-style affinity).
- **Health:** passive only in open source (max_fails plus fail_timeout eject a backend after observed failures); active health checks, sticky cookies, and slow_start are commercial Plus features.
- **Config model:** declarative file (nginx.conf with upstream blocks); changes apply via reload (SIGHUP): the master spawns new workers with the new config while old workers finish in-flight requests and exit. Binary upgrades are separate from reloads.
- **Extra powers:** static file serving, caching, compression, TLS termination, FastCGI and uWSGI bridging. This web-server heritage is exactly why nginx is the default choice when the edge also serves assets or caches responses.
- **Limits:** open-source service discovery is essentially static upstreams or DNS resolution; no native push-based endpoint streams; deep L7 policy (rate limiting at scale, advanced retries) is thinner than Envoy's.

### Family 2: HAProxy
Born as a load balancer and nothing else, with a reputation for raw performance and the deepest health-check and runtime-control toolbox in the self-managed world.
- **Modes:** tcp (L4) and http (L7).
- **Algorithms:** roundrobin (smooth weighted), leastconn, source, uri, hdr, first, static-rr, random, plus dynamic weighting via agent checks.
- **Health:** the industry reference. TCP checks, HTTP checks with expect matching on status or body, external agent checks that report health and weight from the backend itself (a backend can declare itself degraded and lower its own weight), and slowstart ramps for warming servers.
- **Persistence:** cookie modes insert, prefix, rewrite (Topic 5), and stick-tables: in-memory keyed tables that track per-client counters and enable rate limiting, session pinning, and abuse detection at the LB itself.
- **Runtime control:** a Unix stats socket exposes live operations: drain a server, set weights, disable backends, dump stats as CSV, all without reloads. This is why operators who need surgical runtime control love HAProxy.
- **Reload model:** seamless reloads by passing listening sockets from the old process to the new (master-worker mode), so in-flight connections survive config changes better than classic reload designs.
- **Limits:** no web-server features (no static serving or caching), its own configuration DSL to learn, and discovery still file-or-DNS based without external wrappers.

### Family 3: Envoy
Born at Lyft for the microservices era and now the data plane of the service-mesh world and much of the modern gateway world.
- **Config model:** the generational leap. Configuration arrives as streams over the xDS APIs: LDS (listeners), RDS (routes), CDS (clusters), EDS (endpoints), SDS (secrets). No files, no reloads; a control plane (Istio, Contour, Gloo, or a custom Go or Python controller) pushes topology and policy, and Envoy applies it live.
- **Load balancing:** ROUND_ROBIN, LEAST_REQUEST (implemented as power-of-two-choices by default), RING_HASH and MAGLEV (consistent hashing for affinity, Topic 10), RANDOM, plus locality-weighted and zone-aware routing so traffic prefers its own availability zone until pressure forces spill.
- **Resilience primitives built in:** active health checks, outlier detection (passive ejection with max-ejection percentage), circuit breaking per cluster (limits on connections, pending requests, requests, retries), retry budgets with backoff, and the panic threshold: if the healthy percentage of a cluster falls below a threshold (default 85 percent), Envoy ignores health status and spreads traffic across everything, choosing degraded-over-dead.
- **Protocol depth:** native HTTP/2 and gRPC with per-stream load balancing (the Topic 9 lesson implemented correctly), WebSockets, TLS with SDS-driven hot certificate rotation, and mTLS everywhere.
- **Observability:** first-class stats, distributed tracing hooks, and access logs by default; the reason SREs can see per-cluster, per-upstream behavior without agents.
- **Extensibility:** Lua and WebAssembly filters, and ext_proc for out-of-process policy (used heavily by AI gateways).
- **Limits:** steep learning curve, configuration complexity that demands a control plane, and a blast-radius property worth respecting: one bad xDS push can misroute an entire fleet instantly, so control-plane changes need canaries exactly like code.

### Family 4: Managed Cloud Load Balancers
The control plane is the vendor's; you configure intent and the provider runs the fleet.
- **AWS:** ALB (L7: host and path rules, target groups, stickiness, ACM certificates, WAF integration), NLB (L4: ultra-high throughput, static IPs, TLS listeners, IP targets), GWLB (transparent appliance insertion for firewalls), Global Accelerator (anycast entry points riding the AWS backbone to regional endpoints, the managed cousin of Topic 8).
- **GCP:** global external HTTP(S) load balancing with a truly global anycast frontend and backend services spanning regions; regional TCP/UDP proxy and passthrough balancers; internal balancers for east-west.
- **Azure:** Azure Load Balancer (L4), Application Gateway (L7 plus WAF), Front Door (global L7 anycast edge).
- **Common model:** health checks against target groups or backend pools, automatic integration with autoscaling groups and instance lifecycle, IAM-bound configuration, and elastic data planes that grow without your intervention.
- **The fine print that bites in production:** cross-zone load balancing semantics differ (ALB enables it by default; NLB disables it by default, and enabling it incurs inter-AZ data-transfer charges), per-GB and per-hour pricing changes architecture economics, quotas and limits (targets per group, rules per LB) require capacity planning, and even managed data planes need ramp time for extreme instantaneous spikes, so pre-warm or gradual-ramp plans still matter for launch-day events.

### Family 5: The Kubernetes Networking Stack
Kubernetes does not ship one load balancer; it ships an abstraction ladder where several balancers cooperate.
- **Service and kube-proxy:** a Service of type ClusterIP exposes a stable virtual IP; kube-proxy on every node programs either iptables (probability-based random backend selection) or IPVS (real LB algorithms: rr, lc, dh, sh, sed, nq) to DNAT traffic to pod IPs. This is L4, connection-oriented, and distributed per node.
- **Discovery and health integration:** Endpoints and EndpointSlice objects are built from readiness probes (Topic 4). A pod that fails readiness leaves the slices and stops receiving traffic; this is Kubernetes-native health-checked load balancing, and it is why readiness design directly determines rollout safety.
- **NodePort and LoadBalancer:** NodePort opens a port on every node; type LoadBalancer asks the cloud provider to provision a managed cloud LB (Family 4) wired to the nodes or pods, fusing Families 4 and 5 in every cloud deployment.
- **Ingress:** an L7 rules API (host and path) implemented by controllers: nginx-ingress, HAProxy Ingress, Traefik, and Envoy-based Contour, Gloo, and Emissary, or cloud-native controllers that program ALBs directly. The core API is portable; the annotations are controller-specific, which is the classic lock-in trap.
- **Gateway API:** the successor: GatewayClass, Gateway, and HTTPRoute (plus GRPCRoute and others) separate infrastructure roles from application roles, add header and weight-based matching for native canaries, and are becoming the portable standard.
- **Mesh overlay:** Istio or Linkerd add per-call L7 balancing, mTLS, retries, and outlier ejection via Envoy sidecars (Topic 9), and headless Services enable pure client-side discovery.
- **Locality controls:** trafficDistribution (PreferClose) and topology-aware routing keep traffic in-zone when healthy, spilling cross-zone only under pressure, mirroring Envoy's zone-aware logic at platform level.

## Mental Model and Analogy
Think of the five families as five generations of telephone exchanges.
- **Nginx and HAProxy** are electromechanical exchanges with excellent operators: you wire the switchboard by hand (config files), and changes require a careful shift change (reload), but the operators are fast, proven, and cheap.
- **Envoy** is a software-defined exchange: routing tables stream in from a network operations center (xDS control plane) and apply live, with per-call telemetry on every line.
- **Cloud LBs** are the national carrier: you order service, they run the exchange, and you never touch the hardware, but you follow their tariff and their feature catalog.
- **Kubernetes** is the national numbering plan: it does not run one exchange; it defines the numbers (Services), the directory (EndpointSlices), and the rules (Ingress and Gateway API) under which every other exchange in the building operates.

## Real-World Examples

1. **GitHub's HAProxy tiers:** GitHub publicly documented HAProxy as the front door for years, prized for runtime socket control, deep health checks, and predictable performance under absurd load.
2. **Lyft and the birth of Envoy:** Lyft built Envoy because per-team smart clients (Topic 9) had become an upgrade nightmare; the sidecar proxy with a control plane replaced dozens of language-specific resilience libraries, and Istio later adopted Envoy as its data plane.

4. **Cloud-native defaults:** the overwhelming majority of new production deployments start as cloud LB plus Kubernetes Ingress or Gateway API, adding mesh only when mTLS or per-call policy demands it.
5. **gRPC fabrics:** organizations running gRPC internally standardize on Envoy (gateway or sidecar) or gRPC client policies, because per-stream balancing is non-negotiable (Topic 9).

## Internal Working: Mechanics Worth Knowing

1. **Three reload philosophies:** nginx reloads by replacing workers (in-flight requests drain under worker_shutdown_timeout, misconfigured drains drop connections at peak); HAProxy passes listening sockets to the new process for near-seamless handoff; Envoy never reloads because config is data, not process state. Each philosophy defines your change-risk profile.
2. **Passive versus active health per tool:** nginx OSS ejects via observed failures (max_fails, fail_timeout); HAProxy adds synthetic probes plus backend-declared agent health; Envoy combines outlier detection, active checks, and the panic threshold; cloud LBs probe target groups; Kubernetes removes unready pods from EndpointSlices. Same primitive (Topic 4), five dialects.
3. **Stick-tables and rate limiting at the LB:** HAProxy stick-tables track per-source counters enabling HTTP flood control before traffic reaches backends; Envoy delegates global rate limiting to a rate-limit service; cloud LBs integrate WAF and shield products. Where you enforce limits is an architecture decision with cost consequences.
4. **Cross-zone semantics and cost:** ALB spreads across AZs by default; NLB does not, and turning it on bills inter-AZ transfer per GB. Zone-aware Envoy and Kubernetes PreferClose exist to get locality's cost savings without sacrificing availability, spilling cross-zone only under pressure.
5. **Endpoint lag during rollouts:** Kubernetes traffic safety during deploys depends on readiness gates, preStop hooks, and terminationGracePeriodSeconds aligning with EndpointSlice propagation; mismatches produce the classic "pods terminated while still serving" bug.
6. **Blast radius of push config:** xDS and managed control planes apply change fleet-wide in seconds, which is wonderful for rollouts and catastrophic for bad pushes; production teams canary xDS changes and keep last-known-good snapshots exactly as they canary code (Topic 6).

- **Kubernetes:** maximum portability and health integration, paid in abstraction layers that can hide the very mechanics this chapter taught you.
- **The governing trade-off:** control versus ownership. Every step toward managed or API-driven tooling trades tuning depth and transparency for operational leverage; the professional skill is knowing which depth your current scale actually needs.

## Common Misconceptions

1. "Nginx and HAProxy are interchangeable." They overlap heavily but differ decisively: nginx brings web-server powers (cache, static), HAProxy brings LB powers (agent checks, stick-tables, runtime socket). Pick by which powers your edge needs.
2. "Envoy is only for service meshes." Envoy runs as edge gateway, standalone LB, and egress proxy; meshes are one deployment shape among several.
3. "Cloud LBs mean I no longer need load-balancing knowledge." Limits, cross-zone cost semantics, target-health behavior, ramp time, and quota planning all still decide outages and bills.
4. "A Kubernetes Service is a load balancer." It is an abstraction; the balancing is executed by kube-proxy or IPVS, by a cloud LB, by an ingress controller, or by a mesh, and each behaves differently under failure.
5. "Ingress is fully portable." The core API is; annotations are controller dialects. Gateway API improves portability but implementations still vary in features.
6. "Reloads and pushes are free." nginx reloads can drop connections if drains are misconfigured; HAProxy seamless reloads still fork memory; one bad xDS or managed-policy push misroutes everything instantly. Change mechanics are part of the tool's risk profile.

# Topic 13: Load Balancing for AI/ML Workloads

## Intuition First (The Why)
Imagine a restaurant where every order takes a wildly different amount of time to cook: a salad takes one minute, but a slow-roasted brisket takes twelve hours. If the host at the door uses Round Robin to assign orders to chefs, the chef who gets the brisket is blocked for the entire shift while the chef who gets the salad sits idle waiting for the next customer. Furthermore, if a customer orders a brisket, leaves, and comes back an hour later to check on it, they must be sent to the exact same chef, because that chef is the only one who has the meat in their specific oven. 

This is exactly the reality of Large Language Model (LLM) inference. Request costs vary by orders of magnitude (a 10-token summary versus a 100,000-token document analysis). And the "oven" is the GPU's VRAM holding the KV cache, which represents the state of the conversation. Traditional load balancers, designed for uniform, stateless HTTP requests, fail catastrophically here. AI load balancing requires routing based on queue depth, memory pressure, and state affinity.

---

## Detailed Explanation

### Why Traditional Load Balancing Fails for LLMs
1. **Cost Asymmetry:** A standard web API might take 50ms to 200ms per request. An LLM request can take 50ms (short prompt, short generation) or 60 seconds (massive context window, long generation). Round Robin or Least Connections will blindly assign a 60-second job to a GPU that is already processing a 50-second job, while other GPUs sit idle.
2. **Statefulness (The KV Cache):** As an LLM generates tokens, it builds a Key-Value (KV) cache in the GPU's VRAM. This cache represents the attention state of the prompt and previous tokens. If a multi-turn conversation is routed to a different GPU on the second turn, the new GPU must recompute the entire KV cache from scratch, wasting massive compute and spiking Time-To-First-Token (TTFT).
3. **HTTP/2 and gRPC Multiplexing:** As established in Topic 3, gRPC multiplexes many requests over a single TCP connection. A Layer 4 load balancer will pin all inference requests from a single application server to one GPU, completely ignoring the other GPUs in the pool.

### The Metrics That Actually Matter
To balance AI traffic, the router must query the workers for AI-specific telemetry, not just CPU or connection counts:
1. **Pending Queue Depth:** How many requests are waiting in the worker's scheduler queue?
2. **KV-Cache Memory Utilization:** What percentage of the GPU's VRAM is occupied by active KV caches? (If a GPU is at 95% KV-cache capacity, it cannot accept new long-context requests, even if its compute cores are idle).
3. **Running/Waiting Token Counts:** How many tokens are currently being processed in the active batch?
4. **Prefix-Cache Hit Rate:** Does this worker already hold the KV cache for the prefix of the incoming prompt?

### Routing Strategy 1: Load-Aware Routing (Queue Depth and Memory)
The router (often an L7 gateway or a specialized inference router like Ray Serve or vLLM's built-in router) queries each worker's metrics endpoint before assigning a request. 
- It routes the request to the worker with the lowest pending queue depth and sufficient KV-cache headroom.
- This prevents the "brisket" problem by ensuring that heavy requests are distributed to GPUs that are currently empty, rather than piling onto the first available connection.

### Routing Strategy 2: Prefix-Cache Affinity (Soft Stickiness)
Many enterprise applications use massive system prompts (e.g., a 5,000-token legal instruction set) or RAG (Retrieval-Augmented Generation) with large retrieved documents. 
- The router hashes the prefix of the incoming prompt.
- It uses consistent hashing (Topic 10) to route the request to the worker that is most likely to already hold that prefix in its VRAM.
- If the worker is overloaded, the router's "load-aware" veto overrides the affinity, routing to an empty GPU and accepting the cache miss. This is **soft affinity**: locality for performance, never for correctness.

### Routing Strategy 3: Disaggregated Serving (Prefill vs. Decode)
The most advanced architectural shift in LLM serving (seen in systems like DistServe, Splitwise, and Mooncake) separates the two phases of inference into different GPU pools:
1. **Prefill Phase:** Processing the initial prompt. This is highly **compute-bound** (heavy matrix multiplications).
2. **Decode Phase:** Generating the output tokens one by one. This is highly **memory-bandwidth-bound** (reading the KV cache from VRAM).

If both phases run on the same GPU, they interfere with each other, causing latency spikes. In a disaggregated architecture:
- The **Prefill Router** sends the initial prompt to a pool of compute-optimized GPUs.
- The Prefill GPU computes the KV cache and transfers it over a high-speed network (like NVLink or RDMA) to a **Decode Router**.
- The **Decode Router** assigns the KV cache to a memory-optimized GPU, which then streams the generated tokens back to the user.
- The load balancer here must manage the state transfer and ensure the decode phase is routed to the exact node holding the transferred KV cache.

## Mental Model and Analogy
- **Traditional LB:** A ticket dispenser at a deli counter. Everyone takes a number, and the next available clerk serves them, regardless of whether the customer wants a single slice of ham or a full catered banquet.
- **AI Load-Aware Router:** A kitchen expeditor who looks at the current ticket rail for every chef. They assign the banquet order to the chef with an empty rail, and the quick sandwich to the chef who is currently finishing up.
- **Disaggregated Serving:** An assembly line. The prep cooks (Prefill GPUs) chop all the ingredients and pass them in a bowl (KV cache) down the line to the line cooks (Decode GPUs) who plate and serve. The expeditor must route the bowl to the right line cook.

## Real-World Examples

1. **vLLM and SGLang:** These open-source inference engines include built-in routing logic. When deployed in a cluster, the router tracks the KV-cache block utilization of each worker. If a worker's block manager is full, the router stops sending it new requests, preventing Out-Of-Memory (OOM) crashes.
2. **Ray Serve:** Anyscale's Ray Serve uses an L7 HTTP proxy that queries the replicas for their queue lengths. It implements "power-of-two-choices" with queue-depth awareness to balance LLM traffic across a cluster of GPUs.
3. **Triton Inference Server:** NVIDIA's Triton uses an ensemble routing model. A request hits the Triton frontend, which routes it to a specific model instance based on dynamic batching queues, ensuring that requests with similar input shapes are batched together to maximize GPU tensor core utilization.
4. **Mooncake (Kimi/Moonshot AI):** A production-scale disaggregated serving architecture that separates prefill and decode nodes, using a specialized KV-cache transfer protocol over RDMA to move state between pools, drastically lowering Time-To-First-Token (TTFT) for massive context windows.

---

## Internal Working: Mechanics Worth Knowing

1. **Continuous Batching Awareness:** Modern inference engines do not process one request at a time; they use continuous batching (iteration-level scheduling). The router must understand that a GPU processing a batch of 10 requests can still accept an 11th request if the KV-cache memory allows it. The metric is not "active connections" but "available KV-cache blocks."
2. **Prefix Hashing:** To implement prefix caching, the router tokenizes the first N tokens of the prompt and hashes them. It checks a distributed hash table (or local LRU cache) to see which worker holds that prefix block. This turns an LLM routing problem into a consistent hashing problem (Topic 10).
3. **The Thundering Herd on OOM:** If an inference worker runs out of VRAM, it crashes or drops requests. If the router is not aware of KV-cache limits, it will keep sending long-context requests to the dying worker, causing a cascade of 500 errors. The router must enforce strict VRAM quotas per request based on estimated token length.
4. **Cold Start and Model Loading:** Unlike web servers that start in milliseconds, loading a 70B parameter model into GPU VRAM takes minutes. The load balancer must integrate with the orchestrator (like Kubernetes) to keep a buffer of "warm" replicas ready, and drain traffic from a replica minutes before it is scaled down.

## Advantages, Disadvantages, and Trade-offs

- **Load-Aware Routing Advantages:** Maximizes GPU utilization, prevents OOM crashes, equalizes queue wait times.
- **Load-Aware Routing Disadvantages:** Requires the router to speak the inference engine's specific metrics protocol; adds a small latency overhead for the metrics query.
- **Prefix-Cache Affinity Advantages:** Drastically reduces TTFT and compute costs for RAG and system-prompt heavy workloads.
- **Prefix-Cache Affinity Disadvantages:** Can create hotspots if one specific prefix becomes globally viral; requires the "load-aware veto" to prevent melting the cached node.
- **Disaggregated Serving Advantages:** Optimizes hardware spend (buy compute GPUs for prefill, memory GPUs for decode), eliminates prefill-decode interference, minimizes TTFT.
- **Disaggregated Serving Disadvantages:** Massive architectural complexity; requires ultra-low latency networks (RDMA) to transfer KV caches; doubles the routing logic.

---

## Common Misconceptions

1. "GPU Compute Utilization is the best metric for routing." False. A GPU can be at 100% compute utilization but have empty VRAM (processing a tiny batch), or it can be at 10% compute utilization but have 99% full VRAM (holding massive KV caches waiting for decode). Queue depth and VRAM block availability are the correct metrics.
2. "LLM inference is stateless, so any worker can handle any turn." False. The KV cache is state. Losing it means paying the prefill cost again. Multi-turn routing requires affinity or distributed KV stores.
3. "We can just use an AWS ALB for our LLM API." An ALB balances HTTP connections, not inference queue depths. It will blindly route a 100k-token request to a worker that is already busy, causing a timeout, while another worker sits idle. You need an application-layer router that understands inference metrics.
4. "Disaggregated serving is always better." It is only better at massive scale (hundreds of GPUs) where hardware specialization and interference reduction outweigh the network transfer costs of the KV cache. For a single node or small cluster, co-located prefill and decode is simpler and faster.

The industry standard stack for AI load balancing places a specialized L7 gateway (like LiteLLM, Portkey, or a custom Envoy ext_proc filter) in front of the inference engines.
